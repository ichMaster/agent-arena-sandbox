## Findings

### 1. 🟡 LOW — Concurrent broadcasts to the same socket aren't serialized

**File:** `server/websockets.py` (`ConnectionManager.broadcast`, `send_to`)

**Failure scenario:** `broadcast()` is called by whichever connection's task triggered an
event — e.g., X's task calls it to deliver `state_update` to *both* X's and O's sockets. If X
and O act at nearly the same moment (X submits a move right as O sends chat), **two different
tasks** can each call `send_text()` on the *same* recipient socket concurrently, with no lock
serializing them. Per the ASGI spec, a connection's `send()` channel is meant to be driven by
one coroutine at a time; nothing here enforces that when the caller is a *different*
connection's task than the one that owns the socket.

I tried to reproduce a concrete failure (a fake slow socket racing five concurrent broadcasts)
and could not — Python's single-threaded event loop plus how this manager currently drives
sends didn't produce corruption or an exception in that harness, and modern ASGI servers
typically queue sends per connection, so the more likely real-world consequence is
**message reordering** under contention, not a crash. I can't rule out a crash under real
uvicorn + concurrent load, but I have no reproduction showing one.

**Why DEFER, not FIX NOW:** the fix (a per-socket `asyncio.Lock` acquired around every
`send_text`/`close` call, including ones triggered by another connection's task) is a genuine
concurrency-hardening change, not a small self-contained one — and it belongs with v05.01
(Resilience & reconnection), which is explicitly the roadmap phase for this class of hardening
("broadcast prunes a socket that fails mid-send... a dead socket doesn't block delivery to the
rest" is already that phase's DoD language). Pulling it forward without the reconnection-path
context v05.01 also touches risks a narrower fix than the phase warrants. Not exploitable via
any test in this phase's DoD — the MVP's actual usage pattern (turn-based play) makes truly
simultaneous broadcasts to the same socket a low-frequency event even when it does happen.

## Fixes applied

### Fix for Finding 1

**Change:** `server/websockets.py` — `ConnectionManager` now keeps one `asyncio.Lock` per socket
(`self._locks`), created lazily via `_lock_for()` on first use (covering the `send_to`-before-
`connect` ordering from the v03.01 fix, not just already-registered sockets). Every `send_text`/
`close` call in `broadcast()`, `send_to()`, and `close_room()` now runs inside `async with
self._lock_for(ws):`. Lock entries are dropped in `disconnect()` and `_prune()` alongside the
existing owner-map cleanup, so they don't grow unbounded across matches/reconnects.

**Regression test:** `tests/test_websockets.py` — five new tests using a new `ExclusiveWebSocket`
fake that records whether any `send_text()` call started while another was still in-flight:
concurrent `broadcast()` calls, concurrent `send_to()` calls, `send_to()` before the socket is
registered, and lock cleanup on both `disconnect()` and prune. Confirmed all five genuinely fail
against the pre-fix code (`AssertionError: assert not True` for the interleaving tests,
`AttributeError: no attribute '_locks'` for the cleanup tests) and pass against the fix.

**Verification:** full suite 223/223 green, `mypy --strict games server agent tests` clean.

**Architecture impact:** none — `ConnectionManager`'s public method signatures are unchanged; the
locking is an internal implementation detail, not part of the pinned contract.
