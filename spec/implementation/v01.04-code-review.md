## Findings

### 1. 🟠 MEDIUM — Unbounded `chat` message length

**File:** `server/main.py` (`_handle_chat`)

**Failure scenario:** `_handle_chat` only checks `isinstance(message, str) and message` — no upper
bound. A client can send a multi-megabyte `chat` payload; `Repository.log_chat` persists it, and
`ConnectionManager.broadcast` immediately re-sends the full payload to **every** connected socket
in the match, including the sender. Unlike the v01.03 finding on `JoinRequest.player_name` (whose
"blast radius was bounded... no WS broadcast exists yet to echo it further" — true at the time), this
phase removes that caveat entirely: chat is live and broadcast today, so an oversized message is
immediately a bandwidth/rendering problem for every participant in the room, not just a storage
concern for the sender.

**Proposed fix:** reject (via the existing `error` event path, not a crash) a `message` longer than a
reasonable bound (matching `JoinRequest`'s 64-char precedent would be too short for real chat; use
500 characters — generous for a taunt/comment, small enough to bound the broadcast).

### 2. 🟡 LOW — A freed seat can be claimed by an unrelated new joiner before reconnect

**File:** `server/main.py` (`ws_match`'s `finally` block calling `repo.release_seat`)

**Failure scenario:** Player X's connection drops (network blip). `finally` releases X's seat
immediately. Before X reconnects, a **different** browser tab calls `POST /lobby/join` on the same
match (not a spectator) — `assign_seat` sees a free symbol and hands X's old seat to this unrelated
new participant. When X's client attempts to reconnect with its original token, `seat_of` now
returns `None` (the row's `symbol` was reassigned to the interloper's token, not X's) — X is
permanently locked out of the match it was playing.

**Why deferred:** this is exactly the seam roadmap.md assigns to v05.01 ("Release the seat on
disconnect ... allow **a reconnect to reclaim it**" is stated as one v05.01 task, not two split
across phases) — v01.04's own DoD only requires the release half (`ConnectionManager` "disconnect
releasing the seat"), which is correctly implemented and tested. Building "reclaim" now would mean
guessing at v05.01's actual design (a grace period? locking the seat to the token instead of freeing
it outright? distinguishing a clean disconnect from a drop?) rather than letting that phase decide
deliberately. Flagged here so v05.01's reconciliation step sees it as a known, real gap to close —
not something newly discovered.

## What's solid

- The §5.4 move-authority flow is implemented exactly as specified, including the reconciliation
  note's precise correction (read-only `seat_of`, never an assignment) — verified by dedicated tests
  for every refusal path (no-seat, out-of-turn, illegal), each also confirming the board is
  genuinely untouched (not just that an error was returned).
- `ConnectionManager.broadcast` correctly prunes a socket that fails mid-send without aborting
  delivery to the rest — unit-tested against fakes, so this doesn't depend on any fragile real-portal
  behavior.
- A genuine cancellation-safety bug was found and fixed *during* this phase's own execution
  (ARENA-049): a client-initiated drop can arrive as cancellation through an anyio `CancelScope`,
  which `asyncio.shield()` does not protect against — root-caused via minimal reproductions before
  landing `anyio.CancelScope(shield=True)`. This is exactly the class of defect this review pass
  looks for; it was caught and fixed before merge, not left for review to find.
- `current_turn: null` is asserted directly in the winning-move test, not inferred.
- The test suite is honest about a real tooling limitation (concurrent dual-WS-client testing hangs
  under `TestClient`) rather than papering over it with a flaky or misleading test — the workaround
  (one continuous connection, opponent moves injected off-channel) still exhaustively exercises the
  authority flow under test, and the doc trail points to where true concurrent verification belongs
  (v05.02).
- `mypy games server agent` is strict-clean across all 13 source files.
