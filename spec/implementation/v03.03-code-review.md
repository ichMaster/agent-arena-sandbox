## Findings

### 1. 🟠 MEDIUM — Chat self-detection compares the wrong fields, so it always fails

**File:** `web/app.js:203` (`renderChat`)

**Failure scenario:** `const isSelf = sender === mySymbol;`. `mySymbol` is `"X"` / `"O"` / `null`
(from `joined.symbol`). But the **real, released** `server/main.py` (`_handle_chat`, called as
`_handle_chat(websocket, repo, match_id, participant.player_name, payload)`) broadcasts
`chat_message.sender` as **`participant.player_name`** — `"Human"`, an agent profile's `name`
(`"Aggressor"`), etc. — never the seat symbol. `"Human" === "X"` is always `false`. Every chat
message a user sends themselves comes back from the server's own echo and renders as an *other*
message (right-aligned, pink) — the "You" / left/blue self-styling this phase's own DoD requires
("players exchange chat live," with §4.4's explicit self-vs-other styling) never fires, for anyone,
ever. This is squarely this phase's own new code, not a latent issue from an earlier release.

Worth noting separately: web_ui_specification.md §4.4 itself claims "The server broadcasts
`chat_message.sender` as the seat symbol ... not the player name" — that claim is **wrong** against
the real v01.04 code (confirmed by reading `server/main.py` directly, not the doc). It's also
inconsistent with `ui_prototype.html`'s own mockup, which shows a chat `.who` label reading
`"Aggressor-Prime"` — a name, not `"O"`. The doc's prose contradicts both the released
implementation and its own prototype; per this build's standing reconciliation principle, the real
implementation is ground truth.

**Proposed fix:** compare `sender` against `myPlayerName` (already tracked, already the exact value
sent as `player_name` at join) instead of `mySymbol`.

### 2. 🟡 LOW — Name collisions still misattribute "self" after the fix

**File:** `web/app.js` (`renderChat`, post-fix)

**Failure scenario:** `myPlayerName` defaults to the hardcoded `"Human"` for every client — there is
no name-entry UI (out of this phase's, and every prior phase's, scope). Two humans in two browser
tabs, both joining the same match, both default to `sender === "Human"` — each would see the
*other's* messages rendered as their own "you" bubble too. `chat_message`'s wire payload
(architecture.md §6.2) carries only `sender` (name) and `message` — nothing that uniquely identifies
*which connection* sent it (a token, a symbol, a connection id).

**Why deferred:** for this MVP's headline scenarios — human-vs-agent and (once v04 lands)
agent-vs-agent-watched-by-a-human — the human's `"Human"` and the agent's profile name (e.g.
`"Aggressor"`) never collide, so Fix 1 alone resolves the actively-broken case that matters most
right now. The residual human-vs-human collision is a real gap, but closing it needs either a wire
change (adding a stable per-participant identifier to `chat_message`, a seam change requiring an
architecture.md update + contract test) or a client-side name-entry feature — both bigger than a
"fix now" for this phase, and neither obviously this phase's call to make unilaterally.
