## Findings

### 1. 🟠 MEDIUM — Default player name collides across participants

**File:** `web/app.js` (`promptPlayerName`)

**Failure scenario:** `promptPlayerName()` is `window.prompt("Your name?", "Player") || "Player"`
— every single caller of Host/Join/Observe sees the *same literal* pre-filled default, and
accepting a pre-filled prompt with zero typing is the lowest-effort, most likely path a real user
(or a quick manual test) takes. If both participants in a match do this — genuinely the common
case, not a contrived one — `state.myPlayerName === "Player"` on **both** connections. ARENA-103's
`renderChat` derives self vs other by `sender === state.myPlayerName` (the real, tested wire
contract: `chat_message.sender` is `player_name`, reconciled from architecture.md this same
phase). With both names equal to `"Player"`, each side's client renders the *other's* messages as
"you" — left-aligned, blue, "self" styling — exactly backwards, in precisely the feature this
phase's DoD names ("players exchange chat live").

**Why MEDIUM, not HIGH:** chat is explicitly non-authoritative flavor (architecture.md §6) —
nothing about game state, security, or the seat-identity model is affected, and nothing crashes.
But it's a real, easily-triggered correctness bug in the UI's own most central chat behavior, not
an edge case, and it's fully in this phase's scope (the code that causes it was written here).

**Why not a wire-contract fix:** the deeper fix — making `sender` unambiguous — would mean adding
a stable per-connection identifier to `chat_message`'s payload, which is a seam change
(`spec/architecture.md` + a contract test) and out of proportion for what "fix now" means here.
The proportionate, self-contained fix is to stop handing out one shared literal default in the
first place.

**Proposed fix:** generate a distinguishing default (e.g. `Player-<short random suffix>`) per
prompt call instead of the fixed string `"Player"`. Doesn't make a chosen name theoretically
impossible to collide (two users can still both type "Alice"), but closes the *guaranteed*
collision from the shared static default, which is the actual reachable failure mode here.

## What's solid

- **Chat is entirely `.textContent`-based, no `innerHTML` writes of server-provided text anywhere**
  — verified directly in `appendMessage`, the one function that touches message content. No XSS
  surface, consistent with the agent-side prompt-injection finding's spirit (v02.02) even though
  the threat model differs (this is a rendering surface, not a model-input surface).
- **`updateChatEnabled()`'s role gate composes correctly with the connection-state gate** — traced
  both call sites (`setConnected`, the `joined` case) and the `resetBoardAndCards()` reset; a
  same-tab re-host can't inherit the previous match's role because `state.mySymbol` is explicitly
  cleared before the new socket opens.
- **The spectator-move-refusal DoD line has real, executable coverage now**, not just an inherited
  assumption from v01 — `tests/test_ui_observer.py` drives it against a live server and asserts
  the exact `"no seat"` error.
- **System notices never risk self/other misclassification** — `renderSystemNotice` calls
  `appendMessage("system", null, text)`, bypassing `renderChat`'s sender comparison entirely by
  construction, not by convention.
- **The v03.02 review's win-line/state_update ordering guarantee and the v03.01 review's
  stale-socket guard both continue to hold under this phase's additions** — re-traced them against
  the final `app.js`, not assumed frozen from earlier reviews.
