# Code Review & Fix Recommendations — v04.01 (contrasting personas, the theater)

**Date:** 2026-07-21 · **Reviewer:** Claude Sonnet 5, via `/ship-solution`
**Scope:** `profiles/aggressive.yml` (refined), `profiles/cautious.yml` (new), `tests/test_personas.py`.
**Method:** manual adversarial read; concrete failure scenario per finding.

## Recommendation summary

*No findings.* This version adds only YAML data consumed by the already-reviewed `AgentProfile`
(v02.02) and `LLMClient`/prompt seams — no new code path, no new attack surface.

## Findings
None. Both profiles are operator-authored config, not user input: `yaml.safe_load` (no arbitrary
constructors), `extra="forbid"` rejects typo'd keys, and `temperature`/`memory_limit` stay bounded by
the existing `AgentProfile` validators — all pinned by `tests/test_profile.py` since v02.02. A
persona's `system_prompt` is trusted content (authored here, not attacker-controlled), so the v02.02
prompt-injection guard (which frames the *opponent's chat* as non-instruction) remains the correct and
sufficient boundary; personas don't need their own guard against themselves.

## What's solid
`Ironclaw` and `Bastion` are distinct on every axis a persona can vary (name, tone, `temperature`
0.9 vs 0.4, `memory_limit` 12 vs 6) — verified in `test_personas.py`, including that both still drive
the real `create_llm_client` with the SDK patched. Move-contract validity is architecturally
independent of persona text (the shipped `choose_move` retry/fallback validates regardless of what the
model says), so a "bad" persona can degrade banter quality but never gameplay legality — exactly the
isolation the roadmap's DoD relies on.

## Architecture impact
None — no seam, contract, or `.py` behavior changed; pure data + tests.
