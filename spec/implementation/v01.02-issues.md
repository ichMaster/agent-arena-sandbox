# v01.02 — GitHub Issues

Issues for phase **v01.02 — Persistence layer (SQLite)** (version **v01 — Game Core & Server
Foundation**), derived from the per-phase Tasks in [roadmap.md](../roadmap.md) (§v01.02) and the
contracts in [architecture.md](../architecture.md) (§3 server structure, §5.1 data model & the
Repository, §5.2 seat identity, §11 testing strategy, §13 design rationale). This file is scoped to a
single phase; IDs continue from the previous phase (ARENA-004 → **ARENA-005…008**).

This phase gives the server a durable store reached through exactly one seam — the **`Repository`**.
Four tables (`matches`, `participants`, `moves`, `chat_messages`), with `UNIQUE(match_id, symbol)`
making at most one X and one O a *database* guarantee rather than an application convention. The
defining decision is that **live game state is never stored as mutable fields**: the board, whose
turn it is, and whether the game is over are all recovered by replaying the move log through a fresh
`TicTacToe`. That keeps `GameInterface` free of any serialize step and makes state survive a restart,
not just a reconnect.

## v01.02 — Persistence layer (SQLite)

### ARENA-005 — Async SQLite engine, session maker & `init_models`

**Description:**
`server/database.py` — the async SQLAlchemy engine over `sqlite+aiosqlite`, an
`async_sessionmaker(expire_on_commit=False)`, a connect-time `PRAGMA foreign_keys=ON`, and
`init_models()` to create tables ([architecture.md](../architecture.md) §3, §5.1). Touches `server/`
and `pyproject.toml` (new runtime dependencies). No models yet — this is the substrate they need.

**What needs to be done:**
- Add `sqlalchemy[asyncio]` and `aiosqlite` as **declared runtime dependencies** in
  `pyproject.toml` (not hand-installed into `.venv/`).
- `server/database.py`: a `DeclarativeBase` subclass, `create_async_engine` over a **config-driven**
  URL defaulting to `sqlite+aiosqlite:///./arena.db`, and `async_sessionmaker(expire_on_commit=False)`.
- A **connect-time event listener** issuing `PRAGMA foreign_keys=ON` — SQLite disables foreign keys
  per connection by default, so without this the FKs in ARENA-006 are silently unenforced.
- `async def init_models()` creating all tables from the metadata.
- Confirm `.gitignore` already covers `*.db`; the dev database is never committed.

**Dependencies:** None

**Expected result:**
An importable async engine and session factory against which a throwaway database can be created and
torn down in a test.

**Acceptance criteria:**
- [ ] `pip install -e ".[dev]"` still succeeds with the new dependencies declared.
- [ ] **`PRAGMA foreign_keys` reads back as `1` on a fresh connection** — asserted directly, not
      assumed. This is the criterion that makes every later FK test meaningful.
- [ ] `expire_on_commit=False` is set, so an object stays readable after its session commits.
- [ ] The database URL is config-driven with a documented default; no path is hardcoded in a handler.
- [ ] **Unit test:** `init_models()` against a **throwaway** database (temp file or a fresh
      `:memory:` engine per test) creates the schema and never touches the dev `arena.db`.
- [ ] `mypy games server agent` clean under `strict = true`; `pytest` green. No LLM involved.

### ARENA-006 — The four ORM tables & the seat uniqueness constraint

**Description:**
`server/models.py` — ORM models for `matches`, `participants`, `moves` and `chat_messages` exactly as
tabulated in [architecture.md](../architecture.md) §5.1, including the **`UNIQUE(match_id, symbol)`**
constraint on seats. Touches `server/` only.

**What needs to be done:**
- `Match`: `match_id` (PK), `game_type`, `status` (`active`/`finished`), `result`
  (`X`/`O`/`draw`/null), `created_at`.
- `Participant`: `token` (PK), `match_id` (FK), `player_name`, `symbol` (`X`/`O`/null),
  `is_spectator`, `created_at` — plus **`UniqueConstraint("match_id", "symbol")`**.
- `Move`: `id` (PK), `match_id` (FK), `player_symbol`, `move` (the **opaque** payload),
  `created_at` — the ordered log that is the source of truth for board state.
- `ChatMessage`: `id` (PK), `match_id` (FK), `sender`, `message`, `created_at` (non-authoritative).
- Typed mapped columns throughout (`Mapped[...]` / `mapped_column`), so `strict` mypy passes.

**Dependencies:** ARENA-005

**Expected result:**
Four tables that round-trip their rows and enforce their constraints at the database level.

**Acceptance criteria:**
- [ ] Each of the four tables round-trips a row (write → read back, all columns intact).
- [ ] **A second seat for the same symbol in the same match is rejected by the database** — an
      `IntegrityError`, not an application-level check.
- [ ] **`UNIQUE(match_id, symbol)` is per match, not global**: the same symbol in a *different* match
      is accepted. A constraint that blocked that would break every concurrent match.
- [ ] **Multiple participants may hold `symbol = NULL` in one match** — observers and unseated
      players must not collide. (SQLite treats NULLs as distinct in a UNIQUE index; this pins it,
      because the opposite behavior would make the second spectator impossible to insert.)
- [ ] A row referencing a non-existent `match_id` is rejected (FK enforced — depends on ARENA-005's
      PRAGMA).
- [ ] **Contract test:** the four table shapes are pinned per §5.1 (table names and key columns).
- [ ] **Unit test:** all of the above against a throwaway database with `foreign_keys=ON`.
- [ ] `mypy games server agent` clean; `pytest` green.

### ARENA-007 — `Repository` — matches, participants & the seat rule

**Description:**
`server/repository.py` — the single seam through which all database access happens; no ad-hoc SQL in
handlers ([architecture.md](../architecture.md) §5.1). This issue covers matches, participants, and
the **seat-by-token rule** of §5.2. Touches `server/` only.

**What needs to be done:**
- `Repository` over one async session: `create_match(match_id, game_type="tictactoe")`,
  `get_match(match_id) -> Match | None` (`None` is what makes a 404 possible at join in v01.03),
  `add_participant(token, match_id, name, is_spectator)`.
- `assign_symbol(match_id, token) -> str | None`, implementing §5.2 **in order**:
  1. participant `is_spectator` → `None` (observers never get a seat, **permanently**);
  2. participant already has a `symbol` → return it (idempotent reconnect);
  3. two seats already taken → `None` (match full);
  4. otherwise assign the first free symbol and **persist** it.
- `release_seat(match_id, token)`.
- The seat is keyed by **`token`**, never by `player_name` — two clients both named `"Human"` must
  get distinct seats.

**Dependencies:** ARENA-006

**Expected result:**
Seats can be claimed, reclaimed and released through the Repository, with the identity rule enforced
by token.

**Acceptance criteria:**
- [ ] `get_match` returns `None` for an unknown id (not an exception) — the caller turns that into a
      404 in v01.03.
- [ ] A spectator token **never** receives a seat, on the first call or any later one.
- [ ] Calling `assign_symbol` twice with the same token returns the **same** symbol (idempotent
      reconnect) and does not consume the second seat.
- [ ] Two distinct tokens receive `X` and `O`; a **third** token receives `None`.
- [ ] **Two participants with the identical display name `"Human"` still get distinct seats** — the
      single highest-value correctness rule in §5.2 and §13.
- [ ] `release_seat` frees the symbol so a later token can take it.
- [ ] **Contract test:** the seat-by-token identity model is pinned (§5.2) — this is a stable seam,
      so `spec/architecture.md` and this test change together.
- [ ] **Unit test:** every branch of the §5.2 algorithm, against a throwaway database. No LLM.
- [ ] `mypy games server agent` clean; `pytest` green.

### ARENA-008 — Move/chat log, `reconstruct_game` & derived `current_turn`

**Description:**
Complete the Repository with the move and chat logs and the **reconstruct-by-replay** rule that is
this phase's defining decision ([architecture.md](../architecture.md) §5.1, §13). Touches
`server/repository.py` and its tests; imports `games/` but adds nothing to the `GameInterface` seam.

**What needs to be done:**
- `log_move(match_id, symbol, move)` and `log_chat(match_id, sender, message)`, both preserving
  insertion order.
- `reconstruct_game(match_id) -> GameInterface`: load the match's moves **in order** and replay them
  through a **fresh `TicTacToe`** — no serialize/deserialize is added to the seam.
- `current_turn(match_id) -> str | None`: **derived**, and **`None` once the game is over**.
- The move payload stays **opaque** in transit: what is written is what comes back, uninterpreted by
  the Repository.

**Dependencies:** ARENA-007

**Expected result:**
The board, whose turn it is, and the result are all recoverable from the move log alone — and survive
a process restart.

**Acceptance criteria:**
- [ ] After N logged moves, `reconstruct_game` yields the **correct board**, and the right
      `is_game_over()` result for won, drawn and in-progress matches.
- [ ] `current_turn` is `X` on an empty match and alternates by move-count parity.
- [ ] **`current_turn` is `None` once the game is over** — the rule §6.2 depends on, so that v01.04's
      terminal `state_update` can carry `current_turn: null` and no client acts into a closing room.
- [ ] **State survives a process restart** — reopen the same database file in a **new engine** and
      reconstruct the same board. A `:memory:` database cannot show this, so this specific test uses
      a temp **file**.
- [ ] Moves replay **in insertion order**, not in whatever order the rows come back.
- [ ] The move payload round-trips unexamined (opaque to the Repository).
- [ ] **Unit test:** all of the above against a throwaway database. No LLM, no paid call.
- [ ] `mypy games server agent` clean; `pytest` green.

## v01.02 scope notes

**Total effort:** ~12–16 days across 4 issues (S, M, M, L).
**Critical path:** ARENA-005 → ARENA-006 → ARENA-007 → ARENA-008 (the whole phase).
**Phase DoD (roadmap §v01.02):** matches/participants/moves/chat persist to SQLite and survive a
process restart; the board and whose-turn are correctly reconstructed by replaying the move log; a
second seat for the same symbol is rejected by the DB.
**Contracts pinned this phase:** the four table shapes (§5.1) and the seat-by-token identity model
(§5.2). `GameInterface` is **not** touched — reconstruct-by-replay exists precisely so no serialize
step is added to it.

**Reconciliation note (Step 0.5).** Read against the real v01.01 code and its
[code review](v01.01-code-review.md), not just the design:

- **`TicTacToe.current_player` is now `str | None` and returns `None` once the game is over**
  (review finding #1, commit `f5a9ee4`). `Repository.current_turn` should read it **straight
  through** rather than recomputing parity — the `None`-once-over rule now lives in exactly one
  place, which is what that fix was for. ARENA-008 is written to depend on this.
- `TicTacToe.apply_move` refuses every move once the game is over, so a replay of a well-formed move
  log cannot overshoot a terminal position.
- `get_state()` returns a **copy** of the board, so the Repository can hand it out without aliasing
  live state.
- Deferred v01.01 finding #4 (the engine does not enforce turn order) is homed in **v01.04**, which
  owns the §5.4 authority flow. This phase must therefore **not** assume the move log is
  turn-validated; it replays what it is given.

**Model note:** no model is involved in this phase at all. The `LLMClient` seam arrives in v02.01 and
is mocked in every test thereafter — **no paid APIs**, ever.
