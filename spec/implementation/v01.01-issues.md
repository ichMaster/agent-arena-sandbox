# v01.01 — GitHub Issues

Issues for phase **v01.01 — Project skeleton & the game engine** (version **v01 — Game Core &
Server Foundation**), derived from the per-phase Tasks in [roadmap.md](../roadmap.md) (§v01.01) and
the contracts in [architecture.md](../architecture.md) (§2 module layout, §4.1 `GameInterface`,
§11 testing strategy, §12 run model). This file is scoped to a single phase; IDs start the global
sequence (**ARENA-001…004**) — both GitHub and `spec/implementation/` were empty when it was
generated.

This phase stands up the runnable project skeleton and the first of the three stable seams:
**`GameInterface`**, the only way a game enters the system, plus its first concrete implementation,
TicTacToe. Nothing here imports `server/` or any transport — the engine is pure logic, verified in
isolation. It is built now because every later phase (persistence replay, move authority, the agent's
valid-move validation, the UI's board render) treats this seam as fixed.

## v01.01 — Project skeleton & the game engine

### ARENA-001 — Project skeleton, packaging & the tooling gates

**Description:**
Stand up the runnable project: `pyproject.toml` (build backend, explicit package list, pytest and
strict-mypy config) and the package skeleton from [architecture.md](../architecture.md) §2. Touches
the repo root and creates `games/` and `tests/`. No application logic — this issue exists so that
every later issue has a green gate to prove itself against.

**What needs to be done:**
- `pyproject.toml`: `[build-system]` (setuptools), project metadata, and an **explicit**
  `[tool.setuptools] packages = ["games", "server", "agent"]`.
- `[project.optional-dependencies] dev` = pytest (+ `pytest-asyncio`), mypy. Runtime deps that the
  README tells users to run must be **declared**, not hand-installed into `.venv/`.
- `[tool.mypy] strict = true` so the repo-wide gate is `mypy games server agent` with no
  `--config-file` flag and no `mypy.ini`.
- `[tool.pytest.ini_options] testpaths = ["tests"]`.
- Create `games/__init__.py` and `tests/`; confirm `.gitignore` already covers `*.db`, `.venv`,
  caches.
- Verify `python3 -m venv .venv && .venv/bin/pip install -e ".[dev]"` succeeds from a clean checkout.

**Dependencies:** None

**Expected result:**
A clean checkout installs editable in one command, and `pytest` + `mypy games server agent` both run
and report success on the empty skeleton.

**Acceptance criteria:**
- [ ] `pip install -e ".[dev]"` succeeds — **it must not fail with *"Multiple top-level packages
      discovered in a flat-layout"***. `web/`, `profiles/`, `spec/`, `codegen/` are auto-discovered as
      false package candidates unless the package list is pinned explicitly.
- [ ] `mypy games server agent` runs strict from `pyproject.toml` alone; **no `mypy.ini` is created**
      and no `--config-file` flag is needed (mypy treats a missing config as a hard error and would
      silently type-check nothing).
- [ ] **`testpaths = ["tests"]` is set, and `pytest` from the repo root does *not* collect
      `codegen/tests/`.** This repo already contains the tracking system's own suite under
      `codegen/`, which carries its own `codegen/pyproject.toml`; once a root `pyproject.toml` exists
      it becomes pytest's rootdir config and **shadows** the codegen one, so `codegen/tests` would be
      collected without its required `-p pytester` plugin and error. Verified by: `pytest`
      collects only `tests/`, while `pytest -c codegen/pyproject.toml` still runs the tracker suite
      green and independently.
- [ ] **Unit test:** a skeleton/import test asserting the `games` package imports and the tooling
      config resolves (no LLM involved anywhere in this phase — no paid call).
- [ ] Ties to DoD: establishes the "verified in isolation, no server involved" harness the rest of
      the phase is proven in.

### ARENA-002 — `GameInterface` — the abstract game plug-in seam

**Description:**
Define `games/interface.py`: the abstract base class that is **the only way a game enters the
system** ([architecture.md](../architecture.md) §4.1). Four abstract methods, fully typed. Touches
`games/` only — it imports nothing from `server/` and knows nothing of transport. **This is a seam
issue**, so it carries its `spec/architecture.md` pin and its contract test in this same commit.

**What needs to be done:**
- `games/interface.py` — `class GameInterface(ABC)` with the four `@abstractmethod`s exactly as
  pinned in §4.1:
  - `get_state(self) -> dict[str, Any]`
  - `get_valid_moves(self) -> list[Any]`
  - `apply_move(self, player: str, move: Any) -> bool`
  - `is_game_over(self) -> str | None`  (`"X"` | `"O"` | `"draw"` | `None`)
- Document the two seam rules in the class docstring: the **move payload is opaque to transport**
  (only the game module interprets it), and **`apply_move` is the sole legality authority** — it
  returns `False` for illegal input and **never raises**.
- Contract test pinning the four method names, their signatures and return annotations, and that
  `GameInterface` cannot be instantiated directly.

**Dependencies:** ARENA-001

**Expected result:**
A typed abstract seam that a game module implements and that the rest of the system can depend on
without knowing any concrete game.

**Acceptance criteria:**
- [ ] Instantiating `GameInterface` directly raises `TypeError`; a subclass missing any of the four
      methods also fails to instantiate.
- [ ] **Contract test:** the `GameInterface` seam is pinned — the four method names, arities, and
      return type annotations per [architecture.md](../architecture.md) §4.1. This test must change
      only when the seam deliberately changes.
- [ ] **Unit test:** a minimal in-test stub subclass implements all four methods and instantiates
      cleanly (LLM mocked/absent — no paid call).
- [ ] `mypy games server agent` stays clean under `strict = true`; no `Any` leaks beyond the
      deliberately-opaque `move` payload and the `get_state` dict values.
- [ ] Ties to DoD: establishes the seam the engine is verified *through*, not around.

### ARENA-003 — TicTacToe engine — board, turn order & move legality

**Description:**
`games/tictactoe.py` — the first concrete `GameInterface`: a 9-cell board with `X` moving first,
`get_state`/`get_valid_moves`, and `apply_move` as the sole legality authority. Touches `games/`
only; pure logic, no server or transport imports. Terminal detection lands separately in ARENA-004 so
that legality is proven on its own first.

**What needs to be done:**
- `class TicTacToe(GameInterface)` — a 9-element board (index `0–8`), `X` first, turn alternating
  by move parity.
- `get_state()` → the structured board, e.g. `{"board": [...]}` per §4.1.
- `get_valid_moves()` → the list of currently-empty cell indices; it **shrinks by exactly one** per
  applied legal move.
- `apply_move(player, move)` → `True` and mutates on a legal move; **`False` without raising** for
  out-of-range (`<0`, `>8`), occupied cells, and wrong-type payloads (`str`, `None`, `float`, `bool`).
- No serialize/deserialize step is added to the seam — live state is reconstructed by replay
  (§13), so the engine stays minimal.

**Dependencies:** ARENA-002

**Expected result:**
A TicTacToe instance that reports its legal moves, applies legal ones, and rejects every illegal
one by returning `False` rather than raising.

**Acceptance criteria:**
- [ ] `X` moves first; alternating legal moves land on the expected cells.
- [ ] `get_valid_moves()` shrinks correctly — length 9 on a fresh board, 8 after one move, and never
      contains an occupied index.
- [ ] **`apply_move` never raises on bad input.** Parametrized rejection cases: out-of-range
      (`-1`, `9`, `100`), an occupied cell, and wrong types (`"4"`, `None`, `4.0`, `True`) — each
      returns `False` and leaves the board **unchanged**.
- [ ] **Unit test:** exhaustive tests run **directly against the engine**, no server involved and no
      LLM (no paid call).
- [ ] `mypy games server agent` stays clean under `strict = true`.
- [ ] Ties to DoD: "correctly reports valid moves, applies legal moves, rejects illegal ones without
      raising."

### ARENA-004 — Terminal detection — 8 win lines, draw, `is_game_over`

**Description:**
Complete the engine with terminal detection: the eight winning lines (3 rows, 3 columns, 2
diagonals), `"draw"` when the board fills with no line, and `None` while the game is ongoing.
Touches `games/tictactoe.py` and its tests only. This closes the phase DoD and makes the engine
usable as the authority every later phase re-validates against.

**What needs to be done:**
- The 8 winning lines as a module-level constant; `is_game_over()` → `"X"` | `"O"` | `"draw"` |
  `None`.
- `"draw"` is returned only when the board is **full and no line is complete** — a full board with a
  winner reports the winner, not a draw.
- Once the game is over, `get_valid_moves()` and `apply_move` behave coherently (no move is legal
  after a terminal state).
- Exhaustive tests: **a win on every one of the eight lines**, for both `X` and `O`.

**Dependencies:** ARENA-003

**Expected result:**
The engine detects win, loss, and draw correctly and reports `None` while play continues — the
phase's DoD, verified with no server involved.

**Acceptance criteria:**
- [ ] **Win detected on each of the 8 lines** (3 rows, 3 columns, 2 diagonals), asserted for both
      symbols — parametrized, one case per line.
- [ ] Draw detection: a full board with no line returns `"draw"`; a full board *with* a line returns
      the **winner**, never `"draw"`.
- [ ] `is_game_over()` returns `None` for a fresh board and for any mid-game position.
- [ ] No further move is accepted once the game is over (`apply_move` returns `False`, still without
      raising).
- [ ] **Unit test:** all of the above directly against the engine — no server, no LLM, no paid call.
- [ ] `mypy games server agent` clean under `strict = true`; `pytest` green.
- [ ] Ties to DoD: "detects win/loss/draw — verified in isolation, no server involved."
