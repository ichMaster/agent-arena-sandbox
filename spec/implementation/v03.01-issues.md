Issues for phase **v03.01 — Static UI shell & connection** (version **v03 — Web UI (Player &
Observer)**), derived from the per-phase Tasks in [roadmap.md](../roadmap.md) (§v03.01) and the

static arena shell (app bar, stage, chat panel — unwired), and `app.js`'s Host/Join/Observe controls

## v03.01 — Static UI shell & connection

### ARENA-097 — Mount `/ui` with `Cache-Control: no-store`

**Description:**
The serving seam every later v03 issue depends on. Touches: `server/main.py`.

**What needs to be done:**
- Mount `StaticFiles(directory="web", html=True)` at `/ui` on the FastAPI `app` (so `/ui/` serves
  `web/index.html`, and `/ui/app.js`, `/ui/styles.css` serve their files directly).
- Add middleware that sets `Cache-Control: no-store` on every response under `/ui/*`, so an edit to
  `web/` is never masked by browser caching (architecture.md §3, §8). Non-`/ui` routes (the REST
  lobby endpoints, `/api/v1/health`) keep their normal (unset) caching — the header must not leak
  onto them.
- `web/` doesn't have real content yet at this point in the dependency order — create a minimal
  placeholder `web/index.html` (a bare valid HTML shell) so the mount has something to serve and
  this issue's own tests pass standalone; ARENA-098 replaces its contents wholesale.

**Dependencies:** None

**Expected result:**
`GET /ui/` returns 200 with `Cache-Control: no-store`; `GET /api/v1/health` does not carry that
header.

**Acceptance criteria:**
- [ ] `/ui/` and `/ui/app.js`-style asset paths are served from `web/` with `Cache-Control:
      no-store` on every response.
- [ ] Non-`/ui` routes (`/api/v1/health`, `/api/v1/lobby/*`) are unaffected — no `no-store` header
      leaks onto them.
- [ ] **Integration test:** `TestClient` requests to `/ui/` and a non-`/ui` route, asserting the
      header is present on one and absent on the other.
- [ ] Ties to phase DoD: "`/ui/*` responses carry `Cache-Control: no-store`."

### ARENA-099 — `app.js`: Host/Join/Observe, WS connect, connection status, `routeEvent` skeleton

**Description:**
Wires the shell to the server: the three lobby actions each call the REST lobby then open one
WebSocket; a connection-status indicator reflects socket state; the full (never truncated) match id
is displayed; a `routeEvent({event, payload})` dispatcher is stubbed (one case per §6.2 event,
bodies filled in by v03.02/v03.03). Touches: `web/`.

**What needs to be done:**
- **Host** → `POST /api/v1/lobby/match` → `POST /api/v1/lobby/join {spectator:false}` → open
  `ws://<host>/ws/match/{match_id}?token=<token>`.
- **Join** → prompt for a match id → `POST /api/v1/lobby/join {spectator:false}` → open the WS.
- **Observe** → prompt for a match id → `POST /api/v1/lobby/join {spectator:true}` → open the WS.
- Connection-status indicator: dot + label reflect the WebSocket's `onopen`/`onclose`/`onerror`
  state (`Connected` / `Disconnected`); update on every transition.
- `setMatchIdDisplay`: renders the **full** match id string — no `.slice`/`.substring`/ellipsis
  shortening anywhere in the display path (web_ui_specification.md §4.1: "Match ID is shown in
  full, never truncated... the exact string copied into the agent CLI").
- `routeEvent({event, payload})`: a `switch`/dispatch stub with one case per server event (`joined`,
  `state_update`, `chat_message`, `game_over`, `error`) wired to the socket's `onmessage`; bodies can
  be no-ops or minimal (e.g. `joined` stores `mySymbol` and calls `setMatchIdDisplay`) — full
  rendering is v03.02 (board) and v03.03 (chat, Observer polish).
- Client-side state per architecture.md §8 / web_ui_specification.md §7: `ws`, `currentMatchId`,
  `myToken`, `myPlayerName`, `mySymbol` — kept in module-level (or a small state object) variables,
  never derived/duplicated game truth.

**Dependencies:** ARENA-098

**Expected result:**
Clicking Host connects a WebSocket, flips the status indicator to "Connected", and displays the
full match id; the `joined` event is received and dispatched through `routeEvent` without error.

**Acceptance criteria:**
- [ ] Host/Join/Observe each perform their documented REST-then-WS sequence, with `spectator` set
      correctly for each (`false`/`false`/`true`).
- [ ] The connection-status dot/label reflect actual socket state (`Connected`/`Disconnected`).
- [ ] The match id is displayed in full — a regression test asserts no truncation helper is applied
      to it anywhere in the served JS.
- [ ] `routeEvent` has a case for every event in architecture.md §6.2's server→client table
      (`joined`, `state_update`, `chat_message`, `game_over`, `error`).
- [ ] **Integration test:** `TestClient` (or a real `live_server` + a raw WS client) drives Host →
      connect → `joined`, asserting the served `app.js` exposes `routeEvent` and the match-id path
      never truncates.
- [ ] Ties to phase DoD: "opening `/ui`, hosting a match, connecting shows 'Connected' and the full
      match id."
