# v03.03 — GitHub Issues

Issues for phase **v03.03 — Chat & the Observer role** (version **v03 — Web UI (Player &
Observer)**), derived from the per-phase Tasks in [roadmap.md](../roadmap.md) (§v03.03), the
contracts in [game_specification.md](../game_specification.md) §3.3 and
[architecture.md](../architecture.md) §8, and the detailed contract in
[web_ui_specification.md](../web_ui_specification.md) (§4.4, §5, §6). IDs continue from v03.02
(ARENA-067) → **ARENA-068…070**.

**Reconciliation (Step 0.5):** v03.01/v03.02 are released (tags through v03.02.00). Two things the
real, released `web/app.js` already does, which this file builds against rather than duplicating:

1. **The Observe → `spectator:true` flow already exists.** ARENA-064 (v03.01) built
   `joinMatch(spectator)`, and the Observe button already calls `joinMatch(true)` (Join calls
   `joinMatch(false)`) — this *is* "a real spectate action distinct from Join that sends
   `spectator:true`" (the roadmap's own v03.03 DoD wording), just implemented as one parameterized
   function rather than a separately-named `spectateMatch()`. roadmap.md's task phrasing ("
   `spectateMatch()` → `promptAndJoin(spectator=true)`") describes function names that were never
   actually built this way in the real code; the *behavior* it specifies is what matters and is
   already satisfied. This file verifies and extends the existing `joinMatch`/`routeEvent`, it does
   not introduce a parallel `spectateMatch`.
2. **The board is already correctly inert for observers**, as an unplanned consequence of
   ARENA-065's/v03.02's `renderBoard` fix (code review #1, commit 15a9fb8): playability requires
   `currentTurn === mySymbol`, and an observer's `mySymbol` is `null` — which can never equal `"X"`/
   `"O"`, so no cell is ever playable for an observer. This phase adds an explicit test for that
   property (it was previously only an indirect consequence, not a verified contract) rather than
   new rendering code.

What's genuinely new this phase: the chat panel goes live (post + render, sender-labelled,
auto-scroll), and the chat **input** is suppressed for Observers specifically (the board was already
handled; chat wasn't).

## v03.03 — Chat & the Observer role

### ARENA-068 — Chat panel — post and render, sender-labelled

**Description:**
The chat form's submit sends a `chat` action; `renderChat` appends `chat_message` events into the
messages panel, styled by sender per web_ui_specification.md §4.4: the message whose `sender` equals
the client's own **seat symbol** (`mySymbol`) renders as "you" (left, blue-tinted, `agent-x` class
regardless of actual symbol — the class names in `ui_prototype.html` are visually left/right, not
literally tied to X/O), everyone else renders right/pink (`agent-o`). New messages auto-scroll the
panel to the bottom. Touches: `web/`.

**What needs to be done:**
- Chat `<form>`'s `submit` handler: `preventDefault()`; guard (socket `OPEN`, `isGameActive` — chat
  is allowed even off-turn, unlike moves, but still needs a live connection); read the input's
  value, skip if empty; send `{"action": "chat", "payload": {"message": ...}}`; clear the input.
  **Does not render the sent message optimistically** (§8: "the UI does not render sent messages
  optimistically") — it appears only when the server's own broadcast echoes it back.
- `renderChat(sender, message)`: append one `<div class="msg ...">` (structure matching
  `ui_prototype.html`'s markup: a `.who` label + a `.bubble`) to `#messages`; class `agent-x` (self,
  left) when `sender === mySymbol`, else `agent-o` (other, right). Auto-scroll: after appending, set
  `messagesEl.scrollTop = messagesEl.scrollHeight`.
- `routeEvent`'s `chat_message` case calls `renderChat(payload.sender, payload.message)` instead of
  being a no-op.

**Dependencies:** None (extends the released chat panel markup from v03.01/ARENA-063 and the
`routeEvent` skeleton)

**Expected result:**
Typing a message and pressing Send (or Enter) posts it; every connected client — including the
sender, once the server echoes it back — sees it rendered with the correct self/other styling, and
the panel auto-scrolls to show it.

**Acceptance criteria:**
- [ ] **Integration test:** the served `app.js` defines `renderChat` and wires the chat form's
  `submit` handler.
- [ ] **Integration test:** the chat-submit handler's source calls `preventDefault` and sends the
  documented `chat` action shape (`{"action": "chat", "payload": {"message": ...}}`).
- [ ] **Integration test:** `renderChat`'s source assigns the `agent-x`/`agent-o` class conditionally
  on `sender === mySymbol` (not a fixed class), and sets `scrollTop = scrollHeight` (auto-scroll).
- [ ] **Integration test:** `routeEvent`'s `chat_message` case is no longer a no-op — it calls
  `renderChat`.

### ARENA-069 — app.js — lobby actions, one socket, routeEvent skeleton (Observe reconciliation + verification)

**Description:**
Per the Step 0.5 reconciliation note above, `joinMatch(spectator)` (ARENA-064, v03.01) already
implements "a real spectate action distinct from Join that sends `spectator:true`" — the Observe
button already calls it with `true`. This issue adds the explicit tests the v03.03 DoD requires for
that behavior (previously untested at this level of specificity) rather than new production code,
and fixes anything the reconciliation surfaces. Touches: `tests/` (and `web/app.js` only if the
verification surfaces a real gap).

**What needs to be done:**
- Confirm (by reading the released `web/app.js`) that Observe and Join both funnel through
  `joinMatch`, differing only in the `spectator` argument, and that `joinLobby`'s REST body threads
  `spectator` through unchanged (already covered structurally by v03.01's tests — this issue adds the
  join **behavior** tests the v03.03 DoD specifically calls for).
- If the reconciliation finds a real gap (e.g., Observe not actually wired, or `spectator` silently
  dropped), fix it in this issue rather than papering over it — but per the note above, none is
  expected.

**Dependencies:** None

**Expected result:**
The distinctness between Join (`spectator:false`) and Observe (`spectator:true`) is verified
end-to-end at the REST-body level, not just "the two buttons call different-looking code."

**Acceptance criteria:**
- [ ] **Integration test:** `POST /api/v1/lobby/join` triggered via the Observe path (simulated by
  calling the served `joinLobby`'s documented behavior/shape) sends `spectator: true`; the Join path
  sends `spectator: false` — both against the real, running `/api/v1/lobby/join` contract
  (architecture.md §6.1), not just a source-text grep.
- [ ] **Integration test:** joining as a spectator against a real match (via the REST endpoint
  directly) yields a participant with `symbol: null` per the already-released `Repository`/`match.py`
  behavior (v01.03) — confirming the seat-identity guarantee the UI's Observer rendering (ARENA-070)
  depends on.

### ARENA-070 — Observer role — spectate, read-only view, no seat

**Description:**
Completes the Observer experience: `symbol === null` suppresses the chat input (in addition to the
board, already correctly inert as of v03.02's code-review fix) and falls back to default X/O player-
card labels without any null-dereference — `initPlayerCards(null)` (already guarded, ARENA-065) is
exercised here for real, by an actual Observer connection rather than only a direct unit-style call.
This closes the v03.03 DoD and is **the v03 release gate**. Touches: `web/`.

**What needs to be done:**
- `routeEvent`'s `joined` case (or a small helper it calls): when `payload.symbol === null`, disable
  the chat input and Send button (`chatInput.disabled = true; chatSend.disabled = true;`); when
  non-null (a Player), enable them (`= false`) — the input/button ship `disabled` by default in the
  static HTML (ARENA-063), so a Player connection must explicitly re-enable them, matching
  web_ui_specification.md §4.4 ("Disabled until the socket is open; ... disabled entirely for
  Observers").
- Confirm (via a live, real-server integration test — not just source inspection, since this is the
  release-gate issue) that: an Observer's `joined` carries `symbol: null`; the board stays fully
  `disabled` throughout; the chat input stays `disabled`; and a spectator's `submit_move`, if sent
  anyway, is refused server-side (already guaranteed by the released `_handle_submit_move`'s `seat_of
  is None` check, v01.04 — this test confirms the UI's guards aren't the *only* thing preventing it).

**Dependencies:** ARENA-068, ARENA-069

**Expected result:**
Clicking **Observe** on a live match (e.g., an agent-vs-agent match orchestrated outside the UI)
shows the board and chat updating live, read-only, with no seat ever claimed and no crash from a
`null` symbol anywhere in the rendering path.

**Acceptance criteria:**
- [ ] **Integration test:** the served `app.js`'s `joined`-handling source disables the chat
  input/send control when `payload.symbol` is `null`.
- [ ] **Integration test (real server):** an Observer connection's `joined` event carries `symbol:
  null`; `state_update`/`chat_message` events still arrive and would render (board/chat stay
  read-only, not silently dropped) — an Observer watches the *same* live stream a Player does, just
  without seat privileges.
- [ ] **Integration test (real server):** a spectator's `submit_move` (sent directly over the socket,
  bypassing the UI's own guard, to test the *server's* independent enforcement) is refused via an
  `error` event, never mutates the board — re-confirming v01.04's guarantee from the UI's own vantage
  point.
- [ ] `pytest` green for the whole phase; no `mypy` target (`web/` is JS).
- [ ] Ties to v03.03 DoD (v03 release gate): players exchange chat live; clicking Observe on an
  agent-vs-agent match shows the board + chat updating live without claiming a seat; a spectator's
  `submit_move` (if forced) is refused server-side.

on the wire, and the server's independent authority — rather than trusting source inspection alone
