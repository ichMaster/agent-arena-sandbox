## Findings

### 1. 🟠 MEDIUM — `assign_symbol` race: concurrent joins can raise instead of resolving to X/O

**File:** `server/match.py` (`assign_symbol`)

**Failure scenario:** `assign_symbol` reads `taken_symbols(match_id)`, then — after an `await`
point — writes via `set_symbol`. Two genuinely concurrent calls for two *different* tokens on the
*same* match can both read `taken_symbols() == set()` before either commits, both pick `"X"`, and
the second `set_symbol` call raises an **unhandled `IntegrityError`** instead of gracefully
resolving to `"O"`. Demonstrated with two independent sessions (as two real WS connections would
use, per architecture.md §10 — "a DB session is opened per WS connection") racing via
`asyncio.gather`:

```
results: ['X', IntegrityError('UNIQUE constraint failed: participants.match_id, participants.symbol')]
```

architecture.md §10 explicitly names this as an expected race ("Seat races are additionally guarded
by `UNIQUE(match_id, symbol)`") — the **DB constraint** is documented as the backstop, but the
**caller** (`assign_symbol`) never catches the resulting `IntegrityError`, so the guard fires as an
unhandled exception rather than a graceful re-resolution.

Not reachable *today* — v01.03's `POST /lobby/join` never calls `assign_symbol` (seat assignment is
deferred to v01.04's WS connect flow, and v04.02's arena-orchestration script explicitly sequences
its two agents' connects specifically to avoid triggering this). But v01.04 is the very next issue
that wires `assign_symbol` into a live, concurrently-reachable connect path, so shipping the race
unhandled hands the next phase a landmine that would surface as a confusing 500 under real
concurrent play — exactly the class of bug hard to catch without a dedicated concurrency test, which
won't happen again until deep into v01.04 or v05.01. Small, self-contained, high-value: fixing it
now is cheaper than debugging it live in v01.04.

**Proposed fix:** catch `IntegrityError` from `set_symbol`, roll back the session, and retry the
read-then-write once — the retry's `taken_symbols` re-read will see the just-committed row and
correctly resolve to the other candidate or `None` (match full).

## Fixes applied

### Fix for Finding 1

**Change:** `assign_symbol` now catches `IntegrityError` from `set_symbol`, rolls back via a new
`Repository.rollback()`, and retries the read-then-write once.

**Regression test:** `tests/test_match.py::test_concurrent_assign_symbol_resolves_without_raising`
— two independent sessions (mirroring two real WS connections) race `assign_symbol` for two distinct
tokens on the same match via `asyncio.gather`; asserts both calls return without raising and the two
results are `{"X", "O"}`.

**Verification:** full suite green, `mypy --strict games server tests` clean.

**Architecture impact:** none — `assign_symbol`'s signature and `"X" | "O" | None` contract are
unchanged; this closes a gap between the documented guard (§10: "guarded by
`UNIQUE(match_id, symbol)`") and the code that's supposed to handle it, it doesn't change the
guard itself. No update to `spec/architecture.md` needed.
