## Findings

### 1. 🟠 MEDIUM — `match_view` reconstructs the game twice

**Anchor:** [server/match.py](../../server/match.py) — `match_view`

```python
game = await repository.reconstruct_game(match_id)          # SELECT + replay
return MatchView(
    board=...,
    current_turn=await repository.current_turn(match_id),   # SELECT + replay, again
    ...
)
```

`Repository.current_turn` calls `reconstruct_game` internally. So every `match_view` issues **two**
`SELECT`s over the move log and runs **two** full replays, to answer questions about the same
position — and the second result is guaranteed to equal the first, since both derive from the same
rows.

**Failure scenario.** Nothing is *wrong* today, which is why this is MEDIUM and not HIGH. The cost is
where it lands: v01.04 broadcasts a `state_update` after **every valid move**, to **every** connected
socket, and each of those goes through `match_view`. A four-connection match (two players, two
observers) turns one move into eight move-log reads where four would do — and the redundancy grows
with both game length and audience size, i.e. exactly with the agent-vs-agent demo this is built for.

It also quietly contradicts the design's own reasoning. §13 justifies reconstruct-by-replay partly on
it being cheap (≤9 moves for TicTacToe); doubling it for no information is the kind of drift that
makes a sound decision look expensive later.

**Proposed fix.** Derive the turn from the game already in hand instead of asking the Repository to
rebuild it. That needs a turn accessor that takes a *game* rather than a `match_id`; `current_turn`
keeps its signature for callers that only have an id, and both then share one implementation of the
`None`-once-over rule so v01.02's finding #1 stays fixed in one place.

### 2. 🟠 MEDIUM — the per-request transaction does not exist

**Anchor:** [server/main.py](../../server/main.py) — `get_session`, and every `Repository` method

`get_session` wraps the request in `session_scope`, which commits on success and rolls back on
failure — the shape of a request-scoped transaction. But every `Repository` method already ends in
its own `commit()`, so by the time the request finishes there is nothing left to roll back.

**Failure scenario.** `POST /lobby/join` calls `add_participant` (which commits) and then builds the
response. Any failure after that point — a validation error on the response model, a serialisation
problem, a disconnect — leaves the participant row **committed** while the client receives an error
and holds no token. The row is then a permanent orphan occupying a spectator slot, or worse, a
player slot in a two-seat match.

This is v01.02 review finding #4 arriving at its first real caller, exactly where that finding
predicted it would. It is deferred rather than fixed here because the fix is to stop committing
inside `Repository` and let callers own the transaction — which touches every method and every
v01.02 test that depends on the current behaviour. That is larger than "fix now", and v01.04 is where
it must land anyway, because the move-authority flow needs to write a move **and** the match result
as one unit.

**Home:** v01.04.

### 3. 🟡 LOW — a token can be issued for a match nobody can play

**Anchor:** [server/main.py](../../server/main.py) — `join_match`

Join checks only that the match exists. Joining a match that is already **finished**, or whose two
seats are taken, still returns 200 and a token — one that will never hold a seat. The client learns
this only later, from a `joined` event carrying `symbol: null`, which is indistinguishable from
having joined as an observer.

Not fixed here because §6.1 specifies exactly one failure for this endpoint (404 on an unknown
match), and inventing a 409 would be adding contract that no client is written against yet. v01.04
introduces the `joined` event that would have to carry the distinction.

**Home:** v01.04.

### 4. 🟡 LOW — `validate_token` is unused

**Anchor:** [server/auth.py](../../server/auth.py) — `validate_token`

Written, tested, called by nothing. Its first caller is v01.04's WS connect, where a bad token
becomes a `4001` close. The same shape as `session_scope` last phase — which is worth naming, because
that one was only resolved because a review flagged it.

**Home:** v01.04. If that phase does not use it, delete it.

### 5. 🟡 LOW — CORS allows every origin

**Anchor:** [server/main.py](../../server/main.py) — `add_middleware(CORSMiddleware, allow_origins=["*"])`

§3 explicitly calls for "permissive CORS for local dev", and `allow_credentials=False` keeps the
browser from attaching cookies, so a hostile page cannot act as an existing player. The residual
exposure is that any page can create matches and join them — which is what a local dev server is for.

Recorded rather than fixed: tightening it would need a deployment story the MVP does not have (§12 is
local-first, containerisation out of scope).

**Home:** documented MVP scope.

## What's solid

- **The §6.3 ordering rule is asserted at the row**, not inferred: after a spectator join,
  `is_spectator` is set while `symbol` is still `NULL`. That is what makes "an observer can never be
  handed a seat" structurally true rather than a rule each caller must remember.
- **A 404 join writes nothing.** Tested — an endpoint that 404s after inserting would be a slow leak.
- **`extra="forbid"` on the schemas.** A typo'd `spectatr` is refused rather than silently ignored;
  ignoring it would have seated someone who explicitly asked to observe.
- **The lifespan choice is enforced by a test that greps the source** for `on_event`, so the
  deprecated hook cannot be reintroduced by a later edit.
- **The no-cache decision is enforced structurally** — `test_the_match_module_keeps_no_registry`
  parses the AST and fails on any module-level container. Prose would not have survived.
- **The seat rule is proven where clients meet it**: two joins both named `"Human"`, over real HTTP,
  with real tokens — the exact shape the UI produces.
- **Tokens carry no player-supplied text**, and uniqueness is asserted over 2000 samples rather than
  two.
- **The app was booted under real `uvicorn`**, not only `TestClient` — which is the only way to catch
  a lifespan that works in-process and nowhere else.

## Fixes applied

### Finding 1 — one reconstruction per view
**Commit:** `486b57e` · **Files:** `server/repository.py`, `server/match.py`, `tests/test_match_seats.py`

`Repository.turn_of(game)` answers the turn from a game **already reconstructed**;
`current_turn(match_id)` now delegates to it. So `match_view` replays once and derives every field
from that single game, while callers holding only an id keep their old signature — and both paths
share one implementation of the `None`-once-over rule, so v01.02's finding #1 stays fixed in exactly
one place rather than being duplicated by the optimisation.

**Regression tests:**
- `test_a_match_view_replays_the_move_log_exactly_once` **counts** `reconstruct_game` calls by
  patching it. Counting rather than inspecting is the point: the redundant replay produced a
  correct result, so no assertion about the *output* could ever have caught it. Against the previous
  code it reports `expected one replay, got 2`.
- `test_the_view_still_reports_the_turn_correctly` walks a real game to a win and checks
  `current_turn`, `result` and `valid_moves` — so the saving cannot be bought with a wrong answer,
  including at the terminal move where `current_turn` must be `None`.

**Verification:** 220 passed (218 → 220) · `mypy games server agent` clean.

**Architecture impact.** No contract changed. One addition worth carrying forward:

> **`Repository.turn_of(game)`** is the turn accessor for callers that already hold a reconstructed
> game; `current_turn(match_id)` remains for those that do not. v01.04's broadcast path should use
> `turn_of`, since it reconstructs once per move and then serialises to every socket.
