## Findings

### 1. 🟡 LOW — Unbounded lobby input

**File:** `server/schemas.py:8-11` (`JoinRequest`)

**Failure scenario:** `POST /api/v1/lobby/join` accepts any-length `player_name`/`match_id` strings
— Pydantic only enforces the `str` type, not a size bound. A client (malicious or just buggy) can
submit a multi-megabyte `player_name`, which `Repository.add_participant` persists straight into
the `participants` table. `match_id` isn't even looked up until after the whole body has been
parsed and validated, so an oversized `match_id` costs a wasted large-string comparison before the
404. Today the practical blast radius is bounded (single-request storage bloat; no WS broadcast
exists yet to echo it further), but v01.04's `joined`/`state_update` events and v01.03's own
"player cards" (coming in v03.02) will display `player_name` to every other participant in the
match — an unbounded value becomes a rendering/bandwidth problem for everyone in the room, not just
the submitter.

**Proposed fix:** bound both fields via Pydantic `Field(min_length=1, max_length=64)` — rejects
empty and oversized values with a `422`, before either ever reaches the Repository.

### 2. 🟡 LOW — `join_match`'s two Repository calls aren't one transaction

**File:** `server/main.py:48-54` (`join_match`)

**Failure scenario:** `add_participant` commits, then (for a non-spectator) `assign_seat` runs as a
separate commit. If the process crashes between the two — or, more realistically at this scope, if
`assign_seat` itself returns `None` because the match happens to be full — the participant row
exists with `is_spectator=False` and `symbol=None` permanently: a real join that never got a seat,
indistinguishable in the DB from "this was always meant to be seatless."

**Why deferred:** this is the *expected* behavior for the "third player" case the v01.03 DoD itself
requires (a third non-spectator join succeeds but is seatless) — there is no bug in the outcome,
only in the fact that a genuine crash-between-commits would produce the same DB state with no way to
tell the two apart. Fixing this properly means either wrapping both calls in one transaction (a
`Repository` API change — combining `add_participant`+`assign_symbol` into one atomic method) or
adding a reconciliation pass, both bigger than "fix now" for a gap whose worst case (a crash in a
few-millisecond window, in an MVP with no compensating retry UI anyway) is already low-probability
and low-consequence. Revisit if v01.04/v05.01's resilience work needs a stronger guarantee here.

## What's solid

- `server/match.py` stays exactly as thin as architecture.md §5.1 describes it — no logic beyond
  the pass-through, verified against the same seat-rule test matrix as the Repository itself.
- `join_match` correctly never calls `assign_seat` for a spectator (checked via `body.spectator`
  before the call, not after), matching the "observers never hold a seat, permanently" rule — and
  the concurrent-assignment race this endpoint can trigger (two simultaneous non-spectator joins) is
  already covered by the v01.02 code-review fix to `assign_symbol`, so no new concurrency work was
  needed here.
- The `TestClient` integration tests correctly avoid the app's default (real-file) database: a
  `dependency_overrides` swap plus a non-context-manager `TestClient` means `lifespan`'s
  `init_models()` never fires against `./arena.db` during the suite — confirmed no stray file is
  created.
- Seat outcomes (`X`/`O`/seatless/spectator) are verified directly against the DB, not guessed from
  the join response body — correct, since architecture.md §6.1 only returns `{"token": ...}` from
  `join`.
- `mypy games server agent` is strict-clean across all 12 source files.
