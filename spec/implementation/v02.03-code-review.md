## Findings

### 1. 🟠 MEDIUM — Unhandled `WebSocketDisconnect` on every normal game completion

**File:** `server/main.py:95-102` (`ws_match`'s receive loop)

**Failure scenario:** Observed directly while building ARENA-061's live-server test (`pytest -s`
stderr): once a game reaches `game_over`, `_end_game` calls `close_room`, which closes every
connected socket for the match — **including the socket whose own handler task triggered the
close** (the winning move's own connection is still registered until its `finally` block runs). That
socket's `await websocket.receive_json()` (the next loop iteration) then raises
`WebSocketDisconnect`, which propagates uncaught out of the handler. Starlette's default exception
handling logs this as a full traceback at error level — **on every single completed match**, not
just unexpected drops. In a real deployment this is exactly the kind of noise that causes real
errors to get lost in the log stream (alert fatigue) — the disconnect here is not an error, it's the
expected, designed-for consequence of `close_room`.

**Proposed fix:** catch `WebSocketDisconnect` around the receive loop and let it fall through to the
existing `finally` cleanup quietly — the cleanup logic is already correct and unaffected; only the
unhandled-exception logging changes.

### 2. 🟡 LOW — Abnormal WS closures crash the CLI process

**File:** `agent/agent.py` (`AgentSession.run`)

**Failure scenario:** `async for raw in ws:` ends cleanly on a clean server-initiated close (the
normal `game_over` → `close_room` path, verified by ARENA-061's test), but a genuine network drop or
server crash raises `websockets.exceptions.ConnectionClosedError`, uncaught, crashing the whole
`python agent/agent.py` process with a traceback.

**Why deferred:** no roadmap phase currently scopes agent-side resilience to disconnects — v05.01's
resilience work is entirely about the *server's* connection lifecycle (seat reclaim, `finally`
cleanup, broadcast pruning). A CLI tool crashing loudly and visibly on a genuine infrastructure
failure, rather than silently retrying or hanging, is reasonable MVP behavior — a human is watching
the CLI's stdout in every current use case (human-vs-agent, or v04's orchestrated agent-vs-agent with
tailed logs). Revisit if a later phase adds unattended/long-running agent operation.

## Fixes applied

### Fix 1 — `WebSocketDisconnect` caught quietly around the receive loop

**Change:** `server/main.py` — `ws_match`'s outer `try` now has an `except WebSocketDisconnect:
pass` clause before `finally`. The existing cleanup logic in `finally` is unchanged; only the
unhandled-exception logging is suppressed for this expected outcome.
**Regression test:** `tests/test_ws_endpoint.py::test_ws_match_disconnect_does_not_propagate_as_unhandled_exception`
— calls `ws_match` directly (bypassing FastAPI's DI, which is just call-site metadata) with a fake
socket whose `receive_json()` raises `WebSocketDisconnect`, and asserts the call returns normally.
**Verified the test actually catches the bug** by reverting the fix and confirming the test fails
with the pre-fix code, then re-applying it.
**Verification:** `pytest tests/` → 137 passed (136 + 1 new); `mypy games server agent` → no issues
found in 19 source files.
**Architecture impact:** none — no event/action shape changes; this only changes what gets logged
for an already-designed-for connection-lifecycle outcome.
