## Findings

### 1. 🟠 MEDIUM — Seat leak when the socket dies before `joined` is sent

**File:** `server/main.py:91-113` (`websocket_endpoint`)

**Failure scenario:** ARENA-095 reordered the endpoint so `joined` is sent to a newly-connected
socket *before* that socket is registered with `ConnectionManager` (fixing a real ordering race —
see that issue's report). But `assign_symbol()` runs, and commits a seat in the DB, *before*
either of those steps. If the socket dies in the window between `accept()` and a successful
`joined` send — `manager.send_to()` raising because the client already disconnected, a transient
write error, anything — the `finally` block's cleanup (`manager.disconnect(match_id, websocket,
repo)`) can't find the socket: `ConnectionManager._owners` only ever learns about a socket via
`manager.connect()`, which this code path never reached. `repo.release_seat()` is therefore never
called, and the seat stays assigned to a token whose connection is gone — permanently, since a
2-seat game has no other path to free it. **Demonstrated:** a regression test that makes the
`joined` send fail once (simulating a disconnect in that window) leaves `participant.symbol ==
"X"` after the failed connection, on the code as ARENA-095 left it.

**Why MEDIUM, not HIGH:** narrow window (three DB awaits plus one send), scoped to a single match,
no data corruption or crash — but the blast radius within that match is total: a permanently
stuck seat means the match can never be completed by a real second player. Small and
self-contained to fix without touching any seam.

**Proposed fix:** track whether the socket actually reached `manager.connect()` (`registered`).
In `finally`, if it didn't but a symbol was assigned, release the seat directly via
`repo.release_seat()` — the same effect `manager.disconnect()` would have had, without depending
on state that setup never got to establish.

## What's solid

- **The `joined`-before-registration fix itself (ARENA-095) is correct and narrowly scoped** — it
  closes exactly the race it targeted (a concurrent broadcast beating a socket's own `joined`)
  without weakening any other guarantee; this review's finding is a *gap* the fix left behind, not
  a flaw in the fix's own logic.
- **`decide()`'s retry-then-fallback never stalls the match** — verified end-to-end (ARENA-096)
  with a script that never returns a legal move: every turn correctly exhausts
  `MAX_MOVE_ATTEMPTS` and falls back to `random.choice(valid_moves)`, and `valid_moves` is only
  ever empty when the game is already over (`current_turn is None`), which is exactly the state
  `_handle_event` already guards against acting on — so the `IndexError`-on-empty-list edge case
  this might suggest is not reachable given the server's actual invariants, and isn't worth
  defending against speculatively.
- **The agent never trusts its own proposed move** — `decide()` checks `response.move in
  valid_moves` itself, but the server re-validates independently via `apply_move()` regardless;
  the client-side check is an optimization (fewer round trips to discover an illegal move), not
  the authority.
- **`ScriptedLLMClient` is used everywhere an `AgentSession` could reach its own turn** — verified
  by grep across the whole suite; zero paid API calls in the default run, exactly as CLAUDE.md
  requires.
- **`repo.release_seat()` is idempotent** (keyed by token, sets `symbol=None` unconditionally) —
  the fix below can never double-release incorrectly even if some future change made both cleanup
  paths reachable for the same socket.

**Already scheduled, not new:** two independent broadcasts (e.g. a chat action and a move's
`state_update`) can call `ws.send_text()` on the same socket concurrently from two different
connection-handling coroutines — `ConnectionManager` has no per-socket write serialization. This
is the deferred v01.04 finding already homed to v05.01 resilience work; nothing in v02.03 changes
its scope or urgency, so it is not re-raised here.
