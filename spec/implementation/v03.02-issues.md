# v03.02 — GitHub Issues

Issues for phase **v03.02 — Board & gameplay (Player role)** (version **v03 — Web UI (Player &
Observer)**), derived from the per-phase Tasks in [roadmap.md](../roadmap.md) (§v03.02) and the
contracts in [architecture.md](../architecture.md) (§6.2 WebSocket protocol, §8 Web UI
Architecture) plus [web_ui_specification.md](../web_ui_specification.md) (§4.2-4.3, §6, §11). This
file is scoped to a single phase; IDs continue from the previous phase (ARENA-099 →
**ARENA-100…102**).

This phase makes the shell playable: the 3×3 board renders from server state as real `<button>`
cells, clicking one on your turn submits a move, the board freezes with the result at
`game_over`, and player cards track whose turn it is. No chat yet (v03.03).

**Reconciliation note (Step 0.5):** two real gaps between `web_ui_specification.md` and the
*actual, already-implemented and tested* server contract were found while grounding this phase —
both belong to **v03.03**, not here, since neither affects board/gameplay:

1. **§4.4 claims `chat_message.sender` is the seat symbol** (`"X"`/`"O"`). The real, tested
   behavior (`server/main.py:159`, pinned by `tests/test_ws_chat.py::test_chat_broadcasts_to_every_connection_including_sender`,
   unchanged since v01.04) sends `participant.player_name` — e.g. `"Alice"`, never a symbol. The
   self/other chat-styling logic v03.03 implements must compare `sender` against the client's own
   **`myPlayerName`**, not `mySymbol`. `architecture.md` §6.2 itself only says `sender, message`
   with no symbol/name claim, so this doesn't contradict the pinned seam — it's
   `web_ui_specification.md`'s own assumption that's stale.
2. **§4.2 describes a winning-line highlight**, but `game_over`'s payload
   (architecture.md §6.2) is `{result}` only — the server never names which three cells won.
   v03.02's DoD (roadmap §v03.02) doesn't require this highlight, so it's out of scope here; if
   v03.03 or later wants it, the only options are computing it client-side from the final board
   (presentational only, no new authority) or a seam change to add it to the payload — a decision
   for whichever version actually adds it, not this one.

## v03.02 — Board & gameplay (Player role)

### ARENA-100 — `renderBoard`: dynamic cells, marks, playability

**Description:**
Renders the 3×3 board from server-pushed state: creates the nine cell buttons once, then updates
their marks and interactivity on every `joined`/`state_update`. Touches: `web/app.js`.

**What needs to be done:**
- On first render, populate `#board` with nine real `<button id="cell-0">`…`<button id="cell-8">`
  elements (web_ui_specification.md §4.2) — created once, updated in place afterward (never
  recreated per render, so no click-listener churn).
- `renderBoard(board, validMoves, currentTurn, mySymbol, isGameActive)`: for each cell, set its
  mark (`X`/`O`/empty) and CSS class per the §4.2 state table (`empty playable`, `empty disabled`,
  `x`, `o`); a cell is `playable` only when empty **and** `isGameActive` **and**
  `currentTurn === mySymbol` **and** its index is in `validMoves` — otherwise `disabled`
  (real `disabled` attribute, not just a class, per web_ui_specification.md §9 accessibility).
- Observers (`mySymbol === null`): every cell renders `empty disabled` regardless of `currentTurn`
  — never playable (web_ui_specification.md §5).
- Wire into `routeEvent`: `joined` calls `renderBoard` with its payload (replacing v03.01's stub
  body, which only stored `mySymbol`); `state_update` calls it with the fresh `board`/
  `valid_moves`/`current_turn` (replacing v03.01's no-op stub).

**Dependencies:** None (v03.01 already shipped the `#board` container and the `routeEvent`
skeleton this issue fills in)

**Expected result:**
On `joined`, nine cells appear; on each `state_update`, marks and playability update to match the
new board without a page reload.

**Acceptance criteria:**
- [ ] Nine `<button id="cell-0">`…`id="cell-8">` elements render inside `#board`, created once.
- [ ] Each cell's mark/class matches the §4.2 state table for its board value and playability.
- [ ] A cell is playable only when empty, the game is active, it's the human's turn, and the index
      is in `valid_moves`; otherwise it carries the `disabled` attribute.
- [ ] An Observer's board (`mySymbol === null`) is never playable, regardless of `current_turn`.
- [ ] **Integration test:** static assertion on the served `app.js` that `renderBoard` implements
      the playability formula and is called from both the `joined` and `state_update` branches of
      `routeEvent`.
- [ ] Ties to phase DoD: "cells are clickable only on the human's turn."

### ARENA-101 — `handleCellClick` → `submit_move`; `game_over` freeze

**Description:**
Wires clicks on a playable cell to the `submit_move` action, and fleshes out `routeEvent`'s
`game_over` and `error` cases (both v03.01 stubs). Touches: `web/app.js`.

**What needs to be done:**
- `handleCellClick(index)`: guards against sending when the socket isn't `OPEN`, the game isn't
  active, or the cell is `disabled` (web_ui_specification.md §6.3) — a stale/late click after any
  of those must be a silent no-op, never a thrown error or a message sent to a closed socket. On a
  legitimate click, sends `{"action":"submit_move","payload":{"move":index}}`; the board does
  **not** update optimistically — it waits for the server's `state_update` (§8 interaction flows).
- Bind each of the nine cell buttons' `click` listener once, at creation time (ARENA-100), to call
  `handleCellClick` with that cell's index.
- `game_over` case: sets `isGameActive = false`, disables every cell (freezes the board — no
  further clicks possible even if a race lets one through), sets the status label to
  `Game Over — <result>` (web_ui_specification.md §4.1). When `result` is `"X"` or `"O"` (not
  `"draw"`), computes the three winning cells from the already-known final board (client-side,
  presentational only — see this file's reconciliation note on why the server can't supply this)
  and applies the `win` class to them.
- `error` case: extend the v03.01 stub (currently just `console.error`) to also surface the
  `detail` as a visible status-adjacent notice, per web_ui_specification.md §6.1 ("surface a
  system/error line; keep the connection") — the connection itself is never closed on an `error`
  event.

**Dependencies:** ARENA-100

**Expected result:**
Clicking a playable cell submits the move and the board updates only once the server confirms it;
at `game_over` every cell is frozen, the status shows the result, and a real win is highlighted.

**Acceptance criteria:**
- [ ] A click on a playable cell sends exactly one `submit_move` action with that cell's index.
- [ ] Clicks are ignored (no send) when the socket isn't open, the game isn't active, or the cell
      is disabled.
- [ ] The board never updates optimistically — only `state_update` changes what's rendered.
- [ ] `game_over` disables every cell, sets the status label to include the result, and highlights
      the winning line for an `"X"`/`"O"` result (no highlight for `"draw"`).
- [ ] `error` surfaces `detail` visibly without closing the connection.
- [ ] **Integration test:** static assertions on the served `app.js` covering the guard clauses,
      the non-optimistic update, and the `game_over` freeze/highlight logic.
- [ ] Ties to phase DoD: "the board freezes with the result at game over."

### ARENA-102 — Player cards + active-turn highlight; same-tab match reset

**Description:**
Populates the two player-card slots from `joined`, highlights whichever card's symbol matches
`current_turn`, and confirms a new match started in the same tab (Host/Join/Observe clicked again)
resets play state correctly. Touches: `web/app.js`.

**What needs to be done:**
- `initPlayerCards(mySymbol)`: labels the human's own card ("You") and the other card generically
  (its real identity — an agent's persona name — isn't known to the UI in v03.02's scope; a
  placeholder role label is enough here). **Must not crash when `mySymbol` is `null`**
  (web_ui_specification.md §5: an Observer's `initPlayerCards(null)` falls back to default X/O
  labels — never `null.toLowerCase()` or similar).
- Active-turn highlight: the card whose symbol equals `current_turn` gets the `.active` class
  (already styled in `styles.css` from ARENA-098); when `current_turn` is `null` (game over),
  neither card is active. Re-applied on every `state_update` and cleared appropriately at
  `game_over`.
- **Same-tab reset:** ARENA-099 already resets `isGameActive = true` and closes any prior socket
  in `connect()` (code review #1, v03.01) — this issue confirms/extends that the *rendered* state
  resets too: starting a new match re-creates the board fully blank and playable-per-turn (not
  showing the previous match's frozen/`win`-highlighted cells), and both player cards return to
  their default (inactive, unmarked) state before the new match's first `joined` arrives.

**Dependencies:** ARENA-100

**Expected result:**
Player cards show the two seats with the current-turn card visibly highlighted; hosting a second
match in the same tab shows a fresh, fully playable board with no leftover marks or highlights
from the previous game.

**Acceptance criteria:**
- [ ] `initPlayerCards` labels both cards correctly for a Player (`mySymbol` `"X"`/`"O"`) and an
      Observer (`mySymbol` `null`) without crashing.
- [ ] The card matching `current_turn` carries `.active`; neither does when `current_turn` is
      `null`.
- [ ] Starting a new match in the same tab (a second Host/Join/Observe click) renders a blank,
      fully-reset board and player cards — no stale marks, `win` highlights, or `.active` state
      survive from the previous match.
- [ ] **Integration test:** static assertions on the served `app.js` for the null-safe card init
      and the active-turn toggle logic.
- [ ] Ties to phase DoD: "starting a new match in the same tab works without reload."
