## v03.02 — Board & gameplay (Player role)

### ARENA-065 — renderBoard + player cards & active-turn highlight

**Description:**
`renderBoard(board, currentTurn, validMoves)`: draws marks into the 9 existing `#cell-N` buttons and
toggles each cell's playable/disabled state (web_ui_specification.md §4.2); `initPlayerCards(symbol)`
sets up the two player cards' role/name text and marks the card matching `currentTurn` `.active`
(§4.3) — `null` `currentTurn` (game over) leaves neither active, and `initPlayerCards(null)` (the
Observer case, exercised again in v03.03) must not crash. `routeEvent`'s `joined` and `state_update`
cases call these instead of being no-ops. Touches: `web/`.

**What needs to be done:**
- `renderBoard(board, currentTurn, mySymbol, isGameActive)`: for each cell `i`, set `textContent` to
  `board[i]` or empty; class `x`/`o`/`empty`; a cell is playable (`class="empty playable"`, NOT
  `disabled`) only when `board[i] === null && isGameActive && currentTurn === mySymbol` — otherwise
  `disabled` stays set (§4.2's exact playability rule).
- `initPlayerCards(symbol)`: sets the X/O player-card name/role text (`"You" / "Human · Player"` for
  the card matching `symbol`, an opponent placeholder for the other) — falls back to default X/O
  labels without crashing when `symbol` is `null` (never call `null.toLowerCase()` — the exact
  regression web_ui_specification.md §5 calls out).
- `updateActiveCard(currentTurn)`: toggles `.active` on whichever player card's symbol equals
  `currentTurn`; neither is active when `currentTurn` is `null`.
- `routeEvent`'s `joined` case: `initPlayerCards(mySymbol)`, then `renderBoard`/`updateActiveCard`
  from its payload. `state_update` case: `renderBoard`/`updateActiveCard` from its payload (board,
  current_turn, valid_moves).

**Dependencies:** None (extends the released v03.01 shell/skeleton directly)

**Expected result:**
Receiving `joined`/`state_update` correctly draws the board and highlights whichever player card
matches the current turn, with no interactivity wired yet (that's ARENA-066).

**Acceptance criteria:**
- [ ] **Integration test:** the served `app.js` defines `renderBoard`, `initPlayerCards`,
  `updateActiveCard`.
- [ ] **Integration test:** `renderBoard`'s source ties a cell's playable state to
  `currentTurn === mySymbol` (a text-level check on the function body, consistent with this repo's
  served-source testing approach) — not, e.g., always-enabled.
- [ ] **Integration test:** `initPlayerCards`'s source doesn't call a method directly on its
  `symbol` parameter without a null guard (the `null.toLowerCase()` regression class).

### ARENA-066 — handleCellClick → submit_move, with off-turn/finished/closed guards

**Description:**
`handleCellClick(index)`: wired to each board cell's click, sends `{"action": "submit_move",
"payload": {"move": index}}` — but only after guarding against every non-actionable state
(web_ui_specification.md §6.3): the socket isn't `OPEN`, the game isn't active, or the cell is
`disabled`. The UI never renders optimistically — the board only updates from the server's
`state_update` (§8). Touches: `web/`.

**What needs to be done:**
- `handleCellClick(index)`: `if (!ws || ws.readyState !== WebSocket.OPEN || !isGameActive) return;`
  then check the cell's own `disabled` attribute (`if (cell.disabled) return;`) before sending.
- Wire each `#cell-N` button's `click` listener (added once, at init, to all 9 cells) to call
  `handleCellClick(N)`.
- No client-side move-legality check beyond "is this cell currently enabled" — the interactivity
  gate set by `renderBoard` (ARENA-065) **is** the client-side legality signal; the server remains
  the sole authority (architecture.md §5.4) and `web_ui_specification.md` §5 explicitly says the UI
  "must not depend on that as its only guard" from the *server* side, but nothing here second-guesses
  server-issued `valid_moves` — that would be genuine client-side game logic, out of scope (§1: "no
  client-side move validation beyond the interactivity gate").

**Dependencies:** ARENA-065

**Expected result:**
Clicking a playable cell sends exactly one `submit_move`; clicking anywhere else (a disabled cell,
before connecting, after game over) sends nothing.

**Acceptance criteria:**
- [ ] **Integration test:** the served `app.js` defines `handleCellClick` and its source checks
  `ws`/`readyState`/`isGameActive` and the cell's `disabled` state before sending.
- [ ] **Integration test:** the source wires a `click` listener to each of the 9 `#cell-N` buttons
  calling `handleCellClick` with the matching index.
- [ ] **Integration test:** `handleCellClick`'s source sends the documented `submit_move` envelope
  shape (`{"action": "submit_move", "payload": {"move": ...}}`).

### ARENA-067 — Player cards, active-turn highlight & new-match reset

**Description:**
Completes the phase: `routeEvent`'s `game_over` case freezes the board (every cell `disabled`) and
shows the result in the status area + turn banner (§6.1); `error` surfaces a visible line rather than
being silently swallowed. Critically, **`isGameActive` resets to `true` at the start of every new
match** (Host/Join/Observe) in the same tab — web_ui_specification.md §7 names this explicitly as "a
real regression to guard against": without the reset, a second match in the same tab renders every
cell permanently disabled forever, since nothing else ever flips `isGameActive` back to `true`. This
closes the v03.02 DoD. Touches: `web/`.

**What needs to be done:**
- `handleGameOver(result)`: force every cell `disabled`; set `isGameActive = false`; update the
  connection-status label to `"Game Over — <result>"` (§4.1) and the turn banner to a result message.
- `routeEvent`'s `error` case: surface `payload.detail` visibly (a status/turn-banner line at
  minimum — full chat-line surfacing is v03.03's job once the chat panel is live).
- `connectWebSocket` (or `hostMatch`/`joinMatch`, wherever the new-connection flow starts) sets
  `isGameActive = true` **before** the socket opens, so a second hosted/joined match in the same tab
  starts fully interactive again.

**Dependencies:** ARENA-066

**Expected result:**
A full game reaches `game_over`, the board freezes with the result shown; starting a *second* match
in the same browser tab is immediately playable again, not permanently frozen from the first game's
end.

**Acceptance criteria:**
- [ ] **Integration test:** the served `app.js` defines `handleGameOver`; its source disables all
  cells and sets `isGameActive = false`.
- [ ] **Integration test:** the source sets `isGameActive = true` somewhere in the
  host/join/connect flow (the explicit regression guard from web_ui_specification.md §7) — grep for
  `isGameActive = true` outside of variable declaration.
- [ ] **Integration test:** `routeEvent`'s `error` case is no longer a no-op (differs from the
  ARENA-064 skeleton's empty `case "error":` body).
- [ ] `pytest` green for the whole phase; no `mypy` target (`web/` is JS).
- [ ] Ties to v03.02 DoD (release gate): a human hosts a match and plays a full game against a v02
  agent; cells are clickable only on the human's turn; the board freezes with the result at game
  over; starting a new match in the same tab works without reload.
