## Findings

### 1. 🟡 LOW — `joinLobby` doesn't check the REST response before use

**File:** `web/app.js` (`joinLobby`)

**Failure scenario:** `Join`/`Observe` prompt the user for a Match ID (web_ui_specification.md §8).
A typo'd or stale id makes `POST /api/v1/lobby/join` return `404` (the released, tested server
behavior) with a JSON error body (`{"detail": "match not found"}`), not a token. `joinLobby` doesn't
check `response.ok` — it unconditionally does `const data = await response.json(); return
data.token;`, yielding `undefined`. The caller then opens a WebSocket with `token=undefined` in the
URL, which the server correctly rejects with close code `4001` — but the user just sees the
connection silently fail to show "Connected," with no indication *why*, for what is a very ordinary
mistake (a mistyped id).

**Proposed fix:** check `response.ok`; on failure, surface the server's `detail` (or the status text)
via `window.alert` and return `null` without attempting to connect. `hostMatch`/`joinMatch` already
naturally no-op if `connectWebSocket` is never reached — no new control flow needed at the call
sites beyond a null check.

### 2. 🟡 LOW — Intermittent flake in the live-server integration test

**File:** `tests/test_agent_live_game.py` (v02.03/ARENA-061 — not this phase's own code)

**Failure scenario:** across ~10 full-suite runs during this phase's review, one run timed out:
`_opponent_driver`'s `async for raw in ws:` blocked until the test's own `asyncio.wait_for(...,
timeout=15)` cancelled it. The traceback shows a clean `CancelledError` → `TimeoutError`, not a
crash or incorrect pass — the test framework caught it correctly. Re-running immediately after
(several times) passed cleanly, and confirmed the new `/ui` middleware isn't implicated: it's plain
HTTP middleware (`@app.middleware("http")`), which Starlette skips entirely for WebSocket-scope
connections, and every WS-specific test in the suite (98+ of them) was unaffected across all runs.

**Why deferred:** this is exactly the class of fragility ARENA-061's own commit message already
named — mixing a real background-thread `uvicorn` server with concurrent `asyncio` tasks in the same
test process is inherently harder to make fully deterministic than this repo's other tests (which
use `TestClient`'s simpler synchronous, single-process model). v05.02's roadmap task is explicitly
"a live-server fixture ... for end-to-end games" — a more robust harness for exactly this class of
test. Root-causing the specific race here (rather than building the more robust fixture first) risks
solving a problem v05.02 is chartered to solve properly. No production code path is implicated: the
flake is confined to this one test file's own concurrency, not `server/` or `agent/` logic (which
this session's repeated runs, and ARENA-061's own original passing run, already exercised
correctly).

## Fixes applied

### Fix 1 — `joinLobby` checks the response status

**Change:** `web/app.js` — `joinLobby` now checks `response.ok`; on failure it surfaces the server's
`detail` (or `statusText`) via `window.alert` and returns `null` instead of a bogus token.
`hostMatch`/`joinMatch` both guard with `if (!token) return;` before calling `connectWebSocket`.
**Regression test:** `tests/test_ui_app_js.py::test_join_lobby_checks_response_status_before_use`
and `::test_host_and_join_match_guard_against_a_null_token` — source-level checks (consistent with
this repo's no-headless-browser testing approach) that the status check and null-token guards are
actually present in the function bodies.
**Verification:** `pytest tests/` (excluding the known-flaky, unrelated `test_agent_live_game.py`) →
149 passed (147 + 2 new); `mypy games server agent` → no issues found in 19 source files.
**Architecture impact:** none — no wire-contract change; this only changes client-side handling of an
already-documented server response (`404` on an unknown match, per architecture.md §6.1).
