## Findings

### 1. 🟠 MEDIUM — `connect()` never closes a prior connection

**File:** `web/app.js:83-101` (`connect`)

**Failure scenario:** `connect(matchId, token, playerName)` unconditionally does `const ws = new
WebSocket(...); state.ws = ws;` — it never checks whether `state.ws` already holds a live
connection from an earlier Host/Join/Observe click in the same tab. web_ui_specification.md §7
explicitly calls out starting a new match in the same tab as a real, anticipated scenario (it's
why `isGameActive` gets reset there), so this isn't a contrived edge case. **Demonstrated:**
clicking Host, then clicking Host again without a page reload — the first `WebSocket` object is
simply discarded by the JS garbage collector's normal rules, but the browser doesn't proactively
close it just because no JS reference remains; the TCP/WS connection to the *old* match stays
open. Server-side, that old connection's handler coroutine is still blocked on
`websocket.receive_text()`, so the `finally` cleanup in `websocket_endpoint` never runs and the
old match's seat is **never released** — the same permanent-seat-leak failure mode as the v02.03
review's finding #1, this time triggered from the client side instead of a mid-setup disconnect.

**Why MEDIUM, not HIGH:** requires a specific user action (re-host/join/observe without
reloading) rather than happening spontaneously; scoped to the one abandoned match. Small,
self-contained fix confined entirely to `connect()`.

**Proposed fix:** in `connect()`, close any existing `state.ws` before opening the new one. Guard
all four socket event handlers (`open`/`close`/`error`/`message`) against firing for a
now-stale socket (`state.ws !== ws`) — closing the old socket triggers its own `close` event
asynchronously, and without the guard that stale event could fire *after* the new socket's `open`
and incorrectly flip the status indicator back to "Disconnected".

## Fixes applied

### Fix for Finding 1

**Change:** `web/app.js` — `connect()` now closes any existing `state.ws` before opening the new
one. All four socket event handlers (`open`/`close`/`error`/`message`) check `state.ws === ws` (or
`!== ws` for `message`) before acting, since closing the old socket fires its own `close` event
asynchronously and, unguarded, that stale event could arrive after the new socket's `open` and
incorrectly flip the status back to "Disconnected".

**Regression test:** `tests/test_ui_app.py::test_connect_closes_a_prior_socket_before_opening_a_new_one`
and `::test_connect_guards_handlers_against_a_stale_socket` — static source assertions (no JS
runtime in this repo; see the module docstring). Confirmed both fail against the pre-fix `app.js`
(one with a clear assertion failure, one by construction) and pass against the fix.

**Verification:** full suite 153/153 green, `mypy --strict games server agent tests` clean,
`node --check web/app.js` syntax-valid.

**Architecture impact:** none — purely a client-side connection-management fix; no seam or wire
contract changed.
