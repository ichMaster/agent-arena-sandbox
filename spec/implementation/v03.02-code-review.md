## Findings

### 1. 🟡 LOW — `renderBoard` doesn't check `valid_moves`

**File:** `web/app.js` (`renderBoard`)

**Failure scenario:** web_ui_specification.md §4.2 states the playability rule precisely: "A cell is
playable only when it is empty **and** it is the human's turn **and** the game is active **and**
**the move is in `valid_moves`**." The shipped `renderBoard` checks `mark === null && isGameActive &&
currentTurn === mySymbol` — it never reads `valid_moves` at all. For TicTacToe today this produces
identical results (`Repository`/`TicTacToe.get_valid_moves()` is *exactly* the set of empty cells —
no other TicTacToe-specific restriction exists), so there is no active, reachable bug: every case
where the two checks would disagree is unreachable given the current game engine. But it's a real
gap against the documented contract, not a hypothetical one — and architecture.md explicitly designs
for future games (Checkers, Connect 4, Chess) with legality rules that would **not** collapse
"empty" and "in `valid_moves`" the same way.

**Proposed fix:** thread `validMoves` into `renderBoard`'s signature and use
`validMoves.includes(i)` as the playability check, matching the spec's wording exactly rather than
relying on a TicTacToe-specific coincidence.

### 2. 🟡 LOW — No `win` cell highlight (a wire-contract gap, not a UI oversight)

**File:** `web/app.js` (`handleGameOver`), `architecture.md` §6.2 (`game_over` payload)

**Failure scenario:** web_ui_specification.md §4.2's cell-states table documents a `win` state
("green inner glow on the 3 cells") that this phase doesn't render. Investigating *why*: the
`game_over` event's wire payload (architecture.md §6.2, matching the real released
`server/main.py`) carries only `result` (`"X"`/`"O"`/`"draw"`) — **no winning-line information at
all**. Implementing the visual would require the client to independently recompute which 3 cells
formed the line from the final board state — exactly the "no client-side game logic, no derived
board truth" principle web_ui_specification.md §1 rules out, and arguably a bigger violation than
the interactivity gate §10 explicitly permits ("no client-side move validation beyond the
interactivity gate" — win-line computation isn't move validation, it's independently re-deriving
game outcome logic).

**Why deferred:** this isn't a gap this phase's own code introduced or can close — it's a genuine
tension between the visual spec and the wire contract that predates v03.02. Closing it properly
means either (a) the server adding a `winning_line` field to `game_over` (a seam change — updates
architecture.md §6.2 and its contract test, deliberately out of scope for a UI-only phase) or (b) an
explicit decision that the win-glow is cut from MVP scope. Recorded here so whoever makes that call
has the concrete tension on record rather than rediscovering it from a diff against the prototype.

## What's solid

- `initPlayerCards`'s null-safety was verified by **introspecting the function body** for any
  `symbol.<method>()` call, not just by manual inspection — the exact regression class
  web_ui_specification.md §5 names.
- `handleCellClick`'s three guards (socket state, game-active, cell-disabled) are each individually
  asserted in the regression test, not just "a guard exists somewhere."
- `isGameActive`'s reset-on-reconnect (already landed in ARENA-064) is now backed by a dedicated
  regression test tied directly to the exact failure mode web_ui_specification.md §7 calls out by
  name ("a real regression to guard against") — this phase didn't just trust the earlier code, it
  verified the specific property that matters.
- `handleGameOver` correctly clears the active-card highlight (`updateActiveCard(null)`) in addition
  to disabling cells — a detail easy to miss (the spec's own wording: "When `current_turn` is `null`
  ... neither card is active").
- `mypy games server agent` remains strict-clean; `web/`'s tests correctly stay source-level given
  the no-build, no-headless-browser constraints already established in v03.01.
