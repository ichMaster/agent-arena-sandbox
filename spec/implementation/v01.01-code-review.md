## Findings

### 1. 🟠 MEDIUM — `current_player` reports a symbol after the game is over

**Anchor:** [games/tictactoe.py:45-53](../../games/tictactoe.py#L45-L53)

**Failure scenario.** `current_player` counts occupied cells and returns `PLAYERS[played % 2]`
unconditionally. Play `X@0, O@3, X@1, O@4, X@2` — `X` wins on line `(0,1,2)` with five cells filled,
and `current_player` returns `"O"`. Nobody is to move; the game is over.

Today nothing consumes it, so nothing is broken. The risk is what it invites. Its own docstring
advertises it as the rule the server should reuse — *"the same rule lets the server recover whose
turn it is from the move log alone"* — and the next two phases do exactly that:

- v01.02's `Repository.current_turn` is specified as *"derived from move-count parity, `None` once
  over"* (roadmap §v01.02).
- v01.04 requires `current_turn` to be **`null` on the game-ending move** so that *"no client acts
  into a closing room"* ([architecture.md](../architecture.md) §6.2, called out again in §13 as a
  deliberate design decision).

So the engine's own turn accessor currently models the opposite of the contract it is pointing the
implementer at. An implementer who follows the docstring literally produces a terminal `state_update`
carrying `current_turn: "O"`, and the UI enables a board on a finished game. That is a contract
violation that would surface as a confusing client-side bug two phases from where it was introduced.

**Proposed fix.** Return `str | None`, with `None` once `is_game_over()` is not `None` — making the
accessor agree with §6.2 at the point where the rule is easiest to state. Cheap, self-contained, and
it removes the trap rather than documenting it.

**Not a seam change:** `current_player` is a `TicTacToe` convenience, not one of the four
`GameInterface` methods, so no contract test and no `architecture.md` edit are required.

### 2. 🟡 LOW — no `py.typed` marker

**Anchor:** [games/](../../games/)

`games/` is fully annotated and checked under `strict`, but ships no `py.typed`. In-repo that costs
nothing — `mypy games server agent` resolves the source directly. It only bites a consumer that
imports `games` as an *installed* package, which then sees it as untyped. Real, but purely
distribution-facing and worth nothing until packaging is polished.

**Home:** v05.03 (Polish & docs). Not pulled forward.

### 3. 🟡 LOW — `WINNING_LINES` and `BOARD_SIZE` can silently disagree

**Anchor:** [games/tictactoe.py:20-33](../../games/tictactoe.py#L20-L33)

`BOARD_SIZE = 9` is a named constant, which reads as though the geometry were parameterized; the
eight lines are hardcoded 3×3. Changing `BOARD_SIZE` alone would produce a board whose win detection
covers only its first nine cells, with no error.

This is a *false* generality rather than a bug: architecture.md §4.1 is explicit that **new games are
new modules, never generalizations of an existing one**, so `BOARD_SIZE` will never change. Left as
is; the tests pin the eight lines exactly, so a mismatch cannot pass silently.

**Home:** documented MVP scope.

### 4. 🟡 LOW — no turn enforcement; parity mis-answers an out-of-turn log

**Anchor:** [games/tictactoe.py:65-91](../../games/tictactoe.py#L65-L91)

`apply_move` deliberately does not check whose turn it is — architecture.md §5.4 gives turn authority
to the server, and this engine is replayed over an already-ordered move log. That split is correct
and documented.

The residue: if a move log ever *did* contain an out-of-turn move, `current_player`'s parity rule
would return a confidently wrong symbol rather than surfacing the inconsistency. The board `X@0, X@1`
reports `X` to move. This is unreachable while the server holds the line, so it is a robustness
observation about a defense the server owes, not a defect here.

**Home:** v01.04, which builds the §5.4 authority flow and owns the guarantee that the log is
well-ordered.

## What's solid

- **`apply_move` really is total.** Every illegal shape returns `False` and leaves the board
  untouched — verified against out-of-range, occupied, unknown player, and nine wrong types. The
  `bool` case is handled explicitly, which is the one that actually bites: `bool` subclasses `int`,
  so `True` would otherwise be accepted as cell 1.
- **Terminal detection checks the line before fullness**, so a board that fills on a winning move
  reports the winner and not a draw — with a boundary test that wins on the final cell.
- **The win tests are exhaustive in the way that matters**: all eight lines × both symbols, plus a
  two-of-a-line case that would catch an off-by-one ending the game a move early.
- **The contract test pins the seam properly** — method set, abstractness, per-method signatures and
  return annotations, the opaque `move` payload, and a parametrized check that a subclass missing
  *any* one method cannot be instantiated.
- **`get_state()` returns a copy**, so a caller cannot mutate play in place — a small discipline that
  prevents a whole class of aliasing bug once the server starts passing state around.
- **`current_player` is derived, never stored**, consistent with §13's reconstruct-by-replay decision.
- **Tooling gates are guarded by tests, not by convention** — including that `testpaths` stays scoped
  so the tracker's own suite is never swept into the application's.

## Fixes applied

### Finding 1 — `current_player` returns `None` once the game is over
**Commit:** `f5a9ee4` · **Files:** `games/tictactoe.py`, `tests/test_tictactoe_terminal.py`

`current_player` is now typed `str | None` and returns `None` as soon as `is_game_over()` reports a
result. Its docstring now states the §6.2 rule directly — and *why* the `None` is a contract rather
than a convenience — instead of gesturing at parity alone.

**Regression tests** (each would have caught the bug):
- `None` after a win on a line;
- `None` after a win on the **final cell** — the boundary where the winning move is also the
  board-filling one;
- `None` after a draw;
- and, guarding the opposite failure, an ongoing game still names a mover at **every** step of an
  eight-move sequence — so the fix cannot be satisfied by returning `None` too eagerly.

**Verification:** 100 passed (96 → 100) · `mypy games server agent` clean · tracker suite 269 passed.

**Architecture impact.** No contract changed — `current_player` is not one of the four
`GameInterface` methods, so §4.1 and its contract test are untouched and needed no edit. The behavior
change is nonetheless design-relevant, and the next version must build on it:

> **`TicTacToe.current_player` is now `str | None`, and is `None` once the game is over.**

v01.02's `Repository.current_turn` and v01.04's terminal `state_update` should read this value
straight through. It now satisfies §6.2's "`current_turn` is `null` on the game-ending move" *by
construction*, rather than requiring each caller to remember the rule — which is precisely the
failure mode this finding identified.
