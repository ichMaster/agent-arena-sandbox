## Findings

### 1. 🟠 MEDIUM — `apply_move` doesn't check `is_game_over()`

**File:** `games/tictactoe.py:34` (`apply_move`)

**Failure scenario:** `X` wins on move 5 of a game (e.g. top row `0,1,2`). The board still has empty
cells and it is now `O`'s turn per `current_player`. Nothing in `apply_move` consults
`is_game_over()`, so `game.apply_move("O", 3)` **succeeds** — the board keeps changing after the
match has already concluded. `is_game_over()` still correctly reports `"X"` afterward (a completed
line isn't erasable by more marks landing elsewhere), but the board itself no longer reflects the
state at the moment of victory, and further wins for the second player go undetected (a second
3-in-a-row for `O` would make `is_game_over()`'s line scan ambiguous about which player "really"
won first). `architecture.md` §4.1 states `apply_move` is "the sole legality authority" — a finished
game accepting more placements is exactly the kind of illegal transition that authority is supposed
to prevent, even though the phrase's examples (out-of-range/occupied/wrong-type) don't explicitly
name it.

**Proposed fix:** `apply_move` returns `False` immediately if `is_game_over()` is not `None`,
before any other check.

### 2. 🟡 LOW — No encapsulation on `board`/`current_player`

**File:** `games/tictactoe.py:23-24`

**Failure scenario:** Any code holding a `TicTacToe` instance can do `game.board[3] = "X"` or
`game.current_player = "O"` directly, bypassing `apply_move` entirely — including all of its
legality checks (turn order, occupancy, the fix above). `get_state()` already returns a defensive
copy (`list(self.board)`), so this can't happen through the seam's read path — only through a caller
that has the concrete `TicTacToe` object and reaches past the interface.

**Why deferred:** no code outside `games/` holds a `TicTacToe` instance yet (the server that would
do so is v01.02+), so there is no real call site to exploit today. Python has no true private
attributes, so "fixing" this is a naming-convention change (`_board`) plus new read-only accessors —
a small design choice better made once `server/repository.py`'s `reconstruct_game` (v01.02) shows
how the engine is actually held and mutated by its first real caller, rather than guessed at now.
Documented as MVP scope; revisit if `server/` code is ever seen reaching into `.board` directly
instead of through `apply_move`/`get_state`.

## Fixes applied

### Fix 1 — `apply_move` rejects moves once the game is over

**Change:** `games/tictactoe.py` — `apply_move` now returns `False` immediately if
`self.is_game_over() is not None`, before the turn/type/range/occupancy checks.
**Regression test:** `tests/test_tictactoe_terminal.py::test_apply_move_rejected_after_game_over` —
plays out a win, then asserts a further legal-looking move (empty cell, correct next player) is
rejected and the board is unchanged from its winning state.
**Verification:** `pytest tests/` → 32 passed (31 + 1 new); `mypy games` → no issues found in 3
source files.
**Architecture impact:** none — `apply_move`'s signature and return type (`bool`, never raises) are
unchanged; this tightens behavior already implied by "sole legality authority" in architecture.md
§4.1, so no contract text or contract test needed updating.
