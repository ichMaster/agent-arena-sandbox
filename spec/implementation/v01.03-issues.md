# v01.03 — GitHub Issues

Issues for phase **v01.03 — Match, seats & lobby REST** (version **v01 — Game Core & Server
Foundation**), derived from the per-phase Tasks in [roadmap.md](../roadmap.md) (§v01.03) and the
contracts in [architecture.md](../architecture.md) (§3, §5.2 seat identity, §6.1 REST, §6.3 auth
token, §11). IDs continue from the previous phase (ARENA-008 → **ARENA-009…012**).

This phase puts the first real surface on the Repository: a client can create a match and join it,
receiving an **opaque token that *is* the participant id**. The rule that matters is ordering —
`is_spectator` is written onto the participant row **at join, before any seat is assigned**, so an
observer can never be handed a seat by any later code path.

## v01.03 — Match, seats & lobby REST

### ARENA-009 — `IssuedToken`, token issue & validation

**Description:**
`server/auth.py` — the opaque token issued at join and validated at WS connect
([architecture.md](../architecture.md) §6.3). The token **is** the `participant_id` and becomes the
primary key of the `participants` row. Touches `server/` only.

**What needs to be done:**
- `@dataclass(frozen=True) IssuedToken{match_id, player_name, is_spectator=False}`.
- `issue_token(...) -> str` — a random opaque id (MVP; a signed/JWT form is *later* and would not
  change the seam).
- `validate_token(...)` — resolve a token to its participant, or `None` when unknown.
- Tokens are unguessable and unique across calls.

**Dependencies:** None

**Expected result:** a token can be minted at join and resolved back at connect.

**Acceptance criteria:**
- [ ] Two calls never produce the same token (asserted over many iterations, not two).
- [ ] A token carries no player-supplied text — a name must not be recoverable from it, since the
      token is handed to clients and used as an identity.
- [ ] `validate_token` returns `None` for an unknown/blank/malformed token rather than raising.
- [ ] `IssuedToken` is frozen — identity must not be mutable after issue.
- [ ] **Unit test:** all of the above. No LLM.
- [ ] `mypy games server agent` clean; `pytest` green.

### ARENA-010 — Lobby request/response schemas

**Description:**
`server/schemas.py` — Pydantic models for the two lobby endpoints ([architecture.md](../architecture.md)
§6.1). Touches `server/` only.

**What needs to be done:**
- `JoinRequest{match_id: str, player_name: str, spectator: bool = False}`.
- Response models for create (`{match_id}`) and join (`{token}`), plus the `/health` shape.
- Validation: reject an empty `player_name` and an empty `match_id` at the schema boundary.

**Dependencies:** ARENA-009

**Expected result:** malformed lobby input is rejected before it reaches the Repository.

**Acceptance criteria:**
- [ ] `spectator` **defaults to `False`** — a join that omits it is a player, never an observer.
- [ ] Empty/whitespace `player_name` and `match_id` are rejected (422 at the endpoint).
- [ ] An overlong `player_name` is bounded, so a client cannot write unbounded text into the row.
- [ ] Unknown extra fields do not silently become part of the model.
- [ ] **Contract test:** the request/response shapes are pinned per §6.1.
- [ ] **Unit test:** validation cases. No LLM.
- [ ] `mypy games server agent` clean; `pytest` green.

### ARENA-011 — FastAPI app, lifespan & the lobby endpoints

**Description:**
`server/main.py` — the FastAPI app with a `lifespan` context (no deprecated startup hooks) that calls
`init_models()`, plus `GET /api/v1/health`, `POST /api/v1/lobby/match` and `POST /api/v1/lobby/join`
([architecture.md](../architecture.md) §3, §6.1). Touches `server/` only.

**What needs to be done:**
- App + `lifespan` calling `init_models()`; permissive CORS for local dev.
- `GET /api/v1/health` → `{"status": "ok"}`.
- `POST /api/v1/lobby/match` → inserts a `matches` row, returns `{match_id}` (a uuid).
- `POST /api/v1/lobby/join` → **404 if the match is unknown**; inserts a `participants` row carrying
  `is_spectator`; returns `{token}`.
- Adopt `session_scope()` from `server/database.py` for request handling — or delete it (v01.02
  code review finding #5 homed it here).

**Dependencies:** ARENA-010

**Expected result:** create-then-join works over HTTP and returns a seat-bearing token.

**Acceptance criteria:**
- [ ] `GET /api/v1/health` returns `{"status": "ok"}`.
- [ ] Create → join returns a token; the participant row exists with the right `is_spectator`.
- [ ] **Joining an unknown match returns 404**, not 500 and not a token.
- [ ] **`spectator: true` is persisted at join, before any seat assignment** — the ordering rule of
      §6.3 that makes "an observer can never be handed a seat" true by construction rather than by
      every later caller remembering it.
- [ ] `lifespan` creates the schema on startup; no deprecated `@app.on_event` is used.
- [ ] The database path is config-driven, so tests never touch the dev `arena.db`.
- [ ] **Integration test (`TestClient`):** happy path, 404 on a bad match, spectator flagged.
- [ ] `mypy games server agent` clean; `pytest` green. No LLM.

### ARENA-012 — `server/match.py` — seat & turn helpers over the Repository

**Description:**
`server/match.py` — the thin seat/turn helpers over the Repository ([architecture.md](../architecture.md)
§5.1: *"there is no long-lived in-memory `Match` object"*; each action runs against a DB session).
This is what v01.04's WebSocket layer will call. Touches `server/` only.

**What needs to be done:**
- `claim_seat(session, match_id, token)` and `release_seat(session, match_id, token)` over
  `Repository`, plus a helper returning the turn/board view a client needs.
- No caching and no in-memory match registry — every call goes to the database.
- End-to-end coverage of the §5.2 rule **through REST**: two joins get X and O, a third gets none, a
  spectator never does, and two joins both named `"Human"` stay distinct.

**Dependencies:** ARENA-011

**Expected result:** seats can be claimed and released through the same helpers the WS layer will
use, with the identity rule holding end to end.

**Acceptance criteria:**
- [ ] Two distinct tokens get `X` and `O`; a third gets `None`; a spectator token never does.
- [ ] **Two joins sharing the display name `"Human"` get distinct seats** — asserted through the
      REST surface, not just the Repository, so the rule is proven where clients actually meet it.
- [ ] A reconnect with the same token returns the same seat (idempotent).
- [ ] `release_seat` frees the symbol for a later token.
- [ ] **No in-memory match state** — asserted structurally (no module-level match registry/dict), so
      the "reconstruct, don't cache" decision cannot be quietly reversed.
- [ ] **Integration test:** the whole rule exercised through `TestClient`. No LLM.
- [ ] `mypy games server agent` clean; `pytest` green.

## v01.03 scope notes

**Total effort:** ~8–12 days across 4 issues (S, S, M, M).
**Critical path:** ARENA-009 → ARENA-010 → ARENA-011 → ARENA-012.
**Phase DoD (roadmap §v01.03):** creating a match then joining returns a token; joining an unknown
match 404s; two distinct tokens get X and O, a third player gets no seat, and a `spectator:true` join
can never be assigned a seat — even two joins sharing the display name `"Human"` get distinct seats.
**Contracts pinned this phase:** the REST endpoint shapes (§6.1) and the auth token (§6.3). The
seat-by-token model (§5.2) is already pinned by v01.02's contract test and must not drift.

**Reconciliation note (Step 0.5).** Read against the real v01.02 code and its
[code review](v01.02-code-review.md):

- **`Repository.assign_symbol` no longer propagates `IntegrityError`** (review finding #2, commit
  `e6bed72`). Every refusal — spectator, match full, unknown token, lost race — is now signalled by
  returning `None`, so `POST /lobby/join` and ARENA-012's helpers need **no exception handling around
  seating**; `None` is the single no-seat answer.
- **`Repository.current_turn` raises `NotImplementedError`** for a game with no turn rule (finding
  #1). That marks a programming error, not a runtime condition — endpoints must **not** catch it.
- **`session_scope()` is still unused** (finding #5, homed here). ARENA-011 either adopts it for
  request handling or deletes it; leaving it unexercised a second time is not an option.
- **Every Repository method commits on its own** (finding #4, homed to v01.04). This phase does not
  need multi-write atomicity, so it is not addressed here — but ARENA-011 should not build anything
  that assumes a request-wide transaction it does not have.
- `get_match` returning `None` for an unknown id is what ARENA-011 turns into the 404.

**Model note:** no model is involved in this phase. The `LLMClient` seam arrives in v02.01 and is
mocked in every test thereafter — **no paid APIs**, ever.
