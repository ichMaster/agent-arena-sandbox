v01.02.00). `Repository.assign_symbol` (built in v01.02, ARENA-042) already implements the full
§5.2 seat-assignment algorithm and, after the v01.02 code review fix (commit 8da84ba), retries

algorithm (already decided in v01.02's reconciliation note, carried forward here). One drift to
flag: roadmap.md §v01.03 lists the health check as `GET /health`, but architecture.md §6.1's REST
table pins `GET /api/v1/health`. architecture.md is the contract-stability source for wire paths;
this file uses `/api/v1/health` and notes the roadmap wording as informal.

Builds the lobby REST surface and the identity model over the Repository: creating and joining a
match, with seats keyed by token — never by display name.

## v01.03 — Match, seats & lobby REST

### ARENA-044 — IssuedToken, token issue & validation

**Description:**
`server/auth.py`: `IssuedToken` (frozen dataclass: `match_id`, `player_name`,
`is_spectator=False`) and `issue_token`/`validate_token`. For the MVP the token is a random opaque
id — it **is** the `participant_id`, i.e. the primary key of the `participants` row it creates
(architecture.md §6.3). Touches: `server/`.

**What needs to be done:**
- `IssuedToken` frozen dataclass exactly per architecture.md §6.3.
- `issue_token() -> str`: a random opaque id (e.g. `uuid4().hex`) — this becomes the `Participant.token` primary key.
- `validate_token(token: str, participants: ...) -> IssuedToken | None`: for this phase, validation
  is "does a `participants` row with this token exist" — the actual DB lookup lands in ARENA-047's
  endpoint wiring; this issue provides the token-shape/generation primitives and a pure-function
  validator signature that ARENA-047 calls against a real lookup result.

**Dependencies:** ARENA-042 (released `Repository`)

**Expected result:**
`issue_token()` produces opaque, sufficiently-random ids usable as a `participants` primary key.

**Acceptance criteria:**
- [ ] **Unit test:** `issue_token()` produces distinct values across repeated calls (no collision in a large sample) and is a non-empty string.
- [ ] **Unit test:** `IssuedToken` defaults `is_spectator` to `False`.
- [ ] `mypy server` strict-clean.

### ARENA-046 — server/match.py — seat & turn helpers over the Repository

**Description:**
`server/match.py`: the thin seat-rule layer the REST/WS handlers call — `assign_seat(repo,
match_id, token) -> str | None` and `release_seat(repo, match_id, token) -> None`, both direct
pass-throughs to `Repository.assign_symbol`/`Repository.release_seat` (the §5.2 algorithm itself
lives in the Repository, per the v01.02 reconciliation note — this module adds no new logic, only a
stable call surface for the endpoint/handler layer to depend on instead of the Repository
directly). Touches: `server/`.

**What needs to be done:**
- `assign_seat(repo: Repository, match_id: str, token: str) -> str | None`: calls
  `repo.assign_symbol(match_id, token)`.
- `release_seat(repo: Repository, match_id: str, token: str) -> None`: calls
  `repo.release_seat(match_id, token)`.
- No new seat logic — this issue's tests confirm the pass-through is correct and that `match.py`
  imports nothing beyond `Repository`, keeping the seam thin as architecture.md §5.1 describes it.

**Dependencies:** ARENA-042 (released `Repository`)

**Expected result:**
Handler code can depend on `server.match` for seat operations without reaching into
`Repository` directly, with identical behavior to calling the Repository methods themselves.

**Acceptance criteria:**
- [ ] **Unit test:** `assign_seat`/`release_seat` produce identical results to calling the
  underlying `Repository` methods directly (spectator, idempotent reconnect, third-player,
  release-then-reassign — the same cases ARENA-042 already covers, exercised through this thinner
  surface).
- [ ] `mypy server` strict-clean.

### ARENA-047 — FastAPI app, lifespan & the lobby endpoints

**Description:**
`server/main.py`: the FastAPI app with a `lifespan` context (calls `init_models()` on startup — no
deprecated `@app.on_event`), `GET /api/v1/health`, `POST /api/v1/lobby/match`, `POST
/api/v1/lobby/join`. `join` 404s on an unknown match, inserts a `participants` row via
`Repository.add_participant`, and — for a non-spectator — calls `server.match.assign_seat`
immediately so the seat is persisted at join time (the client learns its symbol later, over WS in
v01.04's `joined` event; the REST response itself only returns the token per architecture.md §6.1).
This is the phase's DoD-closing issue. Touches: `server/`.

**What needs to be done:**
- `lifespan(app)`: `async with` context that calls `await init_models()` on entry.
- `GET /api/v1/health` → `{"status": "ok"}`.
- `POST /api/v1/lobby/match` → `Repository.create_match(new uuid)` → `{"match_id": ...}`.
- `POST /api/v1/lobby/join` (`JoinRequest` body): `Repository.get_match(match_id)` is `None` → `404`;
  otherwise `issue_token()` → `Repository.add_participant(token, match_id, player_name,
  is_spectator=spectator)` → if not spectator, `server.match.assign_seat(repo, match_id, token)` →
  `{"token": token}`.
- A FastAPI dependency that yields a `Repository` bound to a request-scoped `AsyncSession` (via
  `server.database.async_session_maker`).

**Dependencies:** ARENA-045, ARENA-046

**Expected result:**
Creating a match then joining returns a token; joining an unknown match 404s; two distinct
non-spectator tokens receive `X` and `O` (verified via the Repository/DB after join, since the
join response itself only carries the token), a third player's join succeeds but is seatless, and a
`spectator:true` join is never assigned a seat — even when two joins share the display name
`"Human"`, they remain distinct participants with distinct seats.

**Acceptance criteria:**
- [ ] **Integration test (`TestClient`):** create → join happy path returns a token.
- [ ] **Integration test:** join on an unknown `match_id` returns `404`.
- [ ] **Integration test:** two joins get distinct tokens and (checked via the DB/Repository) `X` and `O`; a third join succeeds (200, a token) but has no seat; `spectator:true` join is flagged and seatless.
- [ ] **Integration test:** two joins with `player_name: "Human"` get distinct tokens and, if both non-spectator, distinct seats.
- [ ] `pytest` green and `mypy server` strict-clean for the whole phase.
- [ ] Ties to v01.03 DoD (release gate): creating a match then joining returns a token; joining an
  unknown match 404s; two distinct tokens get X and O, a third player gets no seat, and a
  `spectator:true` join can never be assigned a seat — even two joins sharing the display name
  `"Human"` get distinct seats.
