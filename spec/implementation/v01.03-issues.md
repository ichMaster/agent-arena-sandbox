## v01.03 — Match, seats & lobby REST

### ARENA-079 — `server/auth.py` — token issue/validate, `IssuedToken`

**Description:**
Issue an opaque token at join and validate it at connect time, per architecture.md §6.3. The token
**is** the `participant_id` — the primary key of the `participants` row it creates (wired in
ARENA-082). Touches: `server/auth.py`.

**What needs to be done:**
- `server/auth.py`: `@dataclass(frozen=True) class IssuedToken: match_id: str; player_name: str;
  is_spectator: bool = False`.
- `issue_token() -> str`: a random opaque id (e.g. `uuid4().hex`) — the MVP form; a signed/JWT form
  is *later* per architecture.md §6.3 and would not change this seam.
- `validate_token(token: str, match_id: str, repo: Repository) -> Participant | None`: looks up the
  participant by token via the Repository, returns `None` if the token doesn't exist or belongs to
  a different match (used by the WS endpoint in v01.04; a stub-level check here since no live
  session exists yet).

**Dependencies:** ARENA-077

**Expected result:**
`issue_token()` returns a fresh opaque id on every call; `IssuedToken` carries exactly the three
documented fields.

**Acceptance criteria:**
- [ ] `issue_token()` returns a unique string on each call (no collisions across 1000 calls).
- [ ] `IssuedToken` fields match architecture.md §6.3 exactly (`match_id`, `player_name`,
      `is_spectator`, defaulting `False`).
- [ ] `mypy --strict server` passes.

### ARENA-081 — `server/match.py` — `assign_symbol` seat rule + `release_seat`

**Description:**
The seat/identity algorithm over the `Repository`, per architecture.md §5.2 — the non-negotiable
rule that a seat is keyed by token, never display name. Touches: `server/match.py`.

**What needs to be done:**
- `server/match.py`: `async def assign_symbol(repo: Repository, match_id: str, token: str) -> str |
  None`, implementing the exact §5.2 algorithm:
  1. participant `is_spectator` → `None` (observers never get a seat, permanently).
  2. participant already has a `symbol` → return it (idempotent reconnect).
  3. two seats already taken for this match → `None` (match full).
  4. otherwise assign the first free symbol (`X` before `O`) and persist it via the Repository.
- `release_seat(repo, match_id, token)` — thin passthrough to `Repository.release_seat`.
- This requires a `Repository.get_participant(match_id, token)`-style read; add it to
  `server/repository.py` if not already present (a small extension, not a new issue — it's a
  direct dependency of this seat rule).

**Dependencies:** ARENA-077

**Expected result:**
Two distinct tokens joining the same match get `X` and `O`; a third gets `None`; a spectator token
always gets `None`; re-calling for a token that already has a symbol returns the same symbol.

**Acceptance criteria:**
- [ ] Spectator token → `assign_symbol` always returns `None`.
- [ ] Idempotent reconnect: calling `assign_symbol` twice for the same token returns the same
      symbol both times (no reassignment, no duplicate row).
- [ ] Third distinct token on a full match → `None`.
- [ ] Two participants sharing the display name `"Human"` still get **distinct** seats — keyed by
      token, never name.
- [ ] **Unit test** for every branch above, no server/network involved.
- [ ] `mypy --strict server` passes.

### ARENA-082 — `server/main.py` — FastAPI app, `/health`, lobby REST endpoints

**Description:**
Stand up the running FastAPI app: the `lifespan` context that calls `init_models()`, and the lobby
REST surface (architecture.md §6.1). This is the phase's release gate. Touches: `server/main.py`,
`tests/`.

**What needs to be done:**
- `server/main.py`: `app = FastAPI(lifespan=...)`; `lifespan` calls `init_models()` on startup.
- `GET /api/v1/health` → `{"status": "ok"}`.
- `POST /api/v1/lobby/match` → inserts a `matches` row via `Repository.create_match` (a generated
  `match_id`, e.g. `uuid4().hex`), returns `CreateMatchResponse`.
- `POST /api/v1/lobby/join` → `JoinRequest` body; `Repository.get_match` — **404 if unknown**;
  `issue_token()`; `Repository.add_participant(token, match_id, player_name, is_spectator)`;
  `spectator:true` → the participant is created but `assign_symbol` is **never called** for it (it
  stays seatless); returns `JoinResponse{token}`.
- A dependency provider wiring `Repository(session)` from `get_session()` (from
  `server/database.py`) into each route.

**Dependencies:** ARENA-079, ARENA-080, ARENA-081

**Expected result:**
Creating a match then joining it returns a token; joining an unknown match 404s; two joins to the
same match get distinct seat-bearing tokens; a `spectator:true` join never holds a seat.

**Acceptance criteria:**
- [ ] `POST /lobby/match` then `POST /lobby/join` (happy path) returns a token.
- [ ] `POST /lobby/join` against an unknown `match_id` returns **404**.
- [ ] Two distinct joins to the same match get `X` and `O`; a third gets no seat (verified via the
      Repository/`assign_symbol` after join, not asserted on the join response itself — the join
      endpoint issues the token; seat assignment happens at WS connect in v01.04, but this issue's
      integration test calls `assign_symbol` directly after join to confirm the two layers compose).
- [ ] `spectator:true` join is flagged correctly on the created participant row.
- [ ] **Integration test** (`TestClient`): create→join happy path, 404 on bad match, spectator
      participant flagged, `GET /health` returns `{"status": "ok"}`.
- [ ] `mypy --strict server` passes; full suite green.
