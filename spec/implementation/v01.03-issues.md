`init_models`), the lobby REST endpoints (`POST /lobby/match`, `POST /lobby/join`), the opaque

the seat-by-token identity end to end (spectators never seated; two players named `"Human"` still get
distinct seats). No model is involved. Depends on v01.02 (the Repository + schema).

### ARENA-OPUS-SONNET-008 — FastAPI app, lifespan, health & lobby schemas

**Description:**
The app gate — `server/main.py` builds the FastAPI app with a `lifespan` that calls the v01.02
`init_models`, a `GET /api/v1/health` liveness route, and a per-request `Repository` dependency;
`server/schemas.py` holds the lobby request/response Pydantic models. Touches: `server/main.py`,
`server/schemas.py`, `tests/`.

**What needs to be done:**
- `server/main.py`: `FastAPI(...)` app with a `lifespan` context that runs `init_models()` on startup (no deprecated startup hooks, §3); `GET /api/v1/health` → `{"status": "ok"}`; a FastAPI dependency that yields a `Repository` bound to a per-request `AsyncSession` (from v01.02's `async_session_maker`).

- Keep the REST surface under `/api/v1/*`. **Do not** add the `/ui` static mount or CORS — those are v03 scope (stay in-phase).

**Dependencies:** None (v01.03 depends on v01.02, already released).

**Expected result:**
A running FastAPI app whose `lifespan` initializes the DB and whose `GET /api/v1/health` returns `{"status": "ok"}`, with typed lobby schemas ready for the endpoints.

**Acceptance criteria:**
- [ ] `server/main.py` exposes a FastAPI app; `lifespan` calls `init_models()`; `GET /api/v1/health` returns `{"status": "ok"}`.
- [ ] `server/schemas.py` defines `JoinRequest` (with `spectator` defaulting to `False`) and the create/join response models.
- [ ] **Integration test** (`TestClient`): `GET /api/v1/health` → 200 `{"status":"ok"}`; the app starts and `init_models` runs (tables exist) — against a **throwaway DB**, no paid call.
- [ ] mypy (strict) clean on `server/main.py` and `server/schemas.py`.
- [ ] Ties to DoD: the app substrate the lobby endpoints mount on.

### ARENA-OPUS-SONNET-009 — Auth tokens (`auth.py`) & the seat-by-token identity

**Description:**
`server/auth.py` — the opaque join token that **is** the `participant_id` (§6.3), with
`issue_token` / `validate_token` and the `IssuedToken` value object. This realizes the non-negotiable
seat-by-token identity model (§5.2): identity is the token, never the display name. Touches:
`server/auth.py`, `server/repository.py` (a `get_participant` read helper if needed), `tests/`.

**What needs to be done:**
- `server/auth.py`: `issue_token() -> str` (a random opaque id used as the `participants` PK), the frozen `IssuedToken{match_id: str, player_name: str, is_spectator: bool = False}`, and `validate_token(...)` that resolves a token+match to an `IssuedToken` (or `None` if unknown/mismatched) via the Repository.
- If needed for validation, add `Repository.get_participant(token) -> Participant | None` (keeps DB access behind the seam) — a small v01.03 extension.
- Document that the token is opaque for the MVP (a signed/JWT form is *later* and would not change the seam), and `is_spectator` is written at join **before** any seat is assigned.

**Dependencies:** None (uses the v01.02 Repository/models; independent of the app gate).

**Expected result:**
An opaque token equal to the `participant_id`, plus `validate_token` that round-trips a valid token to its `IssuedToken` and rejects unknown/mismatched tokens.

**Acceptance criteria:**
- [ ] `issue_token()` returns a unique opaque id; `IssuedToken` carries `match_id`, `player_name`, `is_spectator` (default `False`); the token is the participant PK.
- [ ] **Contract test:** the seat-by-token identity surface — `IssuedToken` shape and that identity is keyed by token (the participant PK), not by name. *(§5.2/§6.3 implemented as documented — no architecture change.)*
- [ ] **Unit/integration test** (throwaway DB, LLM absent): `validate_token` returns the right `IssuedToken` for a real participant, and `None` for an unknown token or a token from a different match. No paid call.
- [ ] mypy (strict) clean on `server/auth.py` (and any Repository extension).
- [ ] Ties to DoD: the token clients receive at join is the seat-bearing identity.

### ARENA-OPUS-SONNET-010 — Lobby REST — create & join

**Description:**
The lobby endpoints on `server/main.py` (§6.1): `POST /api/v1/lobby/match` inserts a match and
returns its id; `POST /api/v1/lobby/join` validates the match exists (**404 if not**), inserts a
`participants` row carrying `is_spectator`, and returns the opaque **token = `participant_id`**.
Touches: `server/main.py`, `tests/`.

**What needs to be done:**
- `POST /api/v1/lobby/match`: create a `matches` row (a fresh uuid `match_id` via the Repository) and return `{"match_id": ...}`.
- `POST /api/v1/lobby/join`: **404** if `get_match` is `None`; else `issue_token()`, `add_participant(token, match_id, player_name, is_spectator=spectator)`, and return `{"token": ...}`. `spectator: true` writes an observer participant (seat never assigned here).
- Use the `JoinRequest`/response schemas (008) and the token (009). No game state is ever polled over REST.

**Dependencies:** ARENA-OPUS-SONNET-008, ARENA-OPUS-SONNET-009

**Expected result:**
Creating a match then joining returns a token; joining an unknown match returns 404; a `spectator:true` join is flagged as an observer.

**Acceptance criteria:**
- [ ] `POST /api/v1/lobby/match` returns `{"match_id": <uuid>}` and persists the match; `POST /api/v1/lobby/join` returns `{"token": <participant_id>}` and persists the participant with the right `is_spectator`.
- [ ] Joining an unknown `match_id` returns **404**.
- [ ] **Integration test** (`TestClient`, throwaway DB): create→join happy path returns a token; 404 on a bad match; a `spectator:true` join is stored as an observer. No paid call.
- [ ] mypy (strict) clean on the endpoint code.
- [ ] Ties to DoD: creating a match then joining returns a token; joining an unknown match 404s.

### ARENA-OPUS-SONNET-011 — Seat helpers (`match.py`) + end-to-end seat identity

**Description:**
`server/match.py` — the thin seat/turn helpers over the Repository (§2, §5.2): `assign_symbol` /
`release_seat` that manage a session and delegate to `Repository.assign_symbol` / `release_seat`.
This issue proves the **seat-by-token identity end to end** against real join-issued tokens (the
identity tests the v01.02 Repository couldn't, because tokens come from the lobby). Touches:
`server/match.py`, `tests/`.

**What needs to be done:**
- `server/match.py`: `assign_symbol(match_id, token) -> str | None` and `release_seat(match_id, token)` as thin service wrappers that open a session (v01.02 `async_session_maker`), call the Repository's §5.2 methods, and return the result — no in-memory seat state, no re-implementation of the rule.
- End-to-end identity coverage: drive create→join (real tokens) → `assign_symbol`.

**Dependencies:** ARENA-OPUS-SONNET-010

**Expected result:**
Two distinct join tokens get X and O, a third player gets no seat, a spectator can never be seated, and two joins sharing the display name `"Human"` get distinct seats.

**Acceptance criteria:**
- [ ] `server/match.py` exposes `assign_symbol` / `release_seat` as thin helpers over the Repository (the §5.2 rule is not re-implemented).
- [ ] **Integration test** (`TestClient` + throwaway DB): create a match, join twice → the two tokens get `X` and `O`; a third join → no seat; a `spectator:true` join → never seated; two joins both named `"Human"` → **distinct** seats (keyed by token, not name). LLM absent, no paid call.
- [ ] mypy (strict) clean on `server/match.py`.
- [ ] Ties to DoD: two distinct tokens get X and O, a third gets none, a spectator is never seated, and same-name joins stay distinct by token.
