### ARENA-003: TicTacToe engine — board, turn order & move legality
**Status:** completed · **Commit:** `af0c105` · **Attempts:** 1
**Validation:** [x] pytest (52) · [x] mypy · [x] acceptance

9-cell board, `X` first, `current_player` derived from move parity (never stored — the same rule
lets the server recover the turn from the move log alone). `get_state()` returns a copy so callers
cannot mutate play in place. `apply_move` rejects unknown players, non-`int` moves, out-of-range
indices and occupied cells, always by returning `False`.

`bool` is rejected explicitly: it subclasses `int`, so `True` would otherwise be accepted as cell 1.

### ARENA-004: Terminal detection — 8 win lines, draw, `is_game_over`
**Status:** completed · **Commit:** `0878170` · **Attempts:** 2
**Validation:** [x] pytest (96) · [x] mypy · [x] acceptance

`WINNING_LINES` + `DRAW`; a completed line is checked **before** fullness so a board that fills on a
winning move reports the winner. Once over, `get_valid_moves()` is empty and `apply_move` refuses.

**Two attempts.** The first run failed two tests, both test-side:

1. `test_valid_moves_shrink_by_exactly_one_per_move` (from ARENA-003) walked a move sequence that,
   with terminal detection now live, is won by `O` on `(0,1,2)` at the sixth move — so the board
   correctly never filled. Replaced with a drawn line-up. The implementation was **not** weakened to
   accommodate the old assumption.
2. `test_a_full_board_with_a_line_reports_the_winner_not_a_draw` placed the winning row first, which
   ended the game before the remaining cells could be set. The winning cell is now placed last.

Both are the expected cost of splitting legality (ARENA-003) from terminal detection (ARENA-004);
the split was deliberate, so that legality was proven on its own before the game could end.

## Tracking-system fix (outside the issue sequence)

**Commit:** `a2a62ab` — not part of any ARENA issue; recorded here because the run surfaced it.

Creating `server/` in ARENA-001 broke `codegen/tests/test_dashboard.py::test_it_serves_with_the_application_tree_absent`.
The test asserted that `server/`, `games/`, `agent/` and `web/` do **not** exist in the live repo —
true only *between* runs. A generation run creates them, so from the first issue onward the test
would fail, and the property it guards (the dashboard must not depend on the tree it observes) went
unverified exactly when a run could break it.

It now copies `codegen/` into a sandbox with no application siblings, seeds a run there, and serves
from a subprocess so `codegen_root()` genuinely resolves into a tree with no application beside it.
Tracker suite: **269 passed**, mypy and ruff clean.

> Note on the recorded baseline: `run.start` recorded 243 passed / 1 skipped, measured with the
> system interpreter, which lacks `fastapi` and therefore skipped the dashboard tests. Under `.venv`
> the true baseline is 269. The emitted event was left as-is — the log is evidence, and correcting
> it after the fact would defeat its purpose.
