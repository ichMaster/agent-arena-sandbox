## v05.01 — Resilience & reconnection

### ARENA-107 — Per-socket write serialization for broadcast/send_to

**Description:**
Closes the deferred v01.04 finding: `broadcast()` is called by whichever connection's task
triggered an event, so two different tasks can call `send_text()` on the *same* recipient socket
concurrently with nothing serializing them, violating the ASGI expectation that one connection's
send channel is driven by one coroutine at a time. Touches: `server/websockets.py`.

**What needs to be done:**
- Add a per-socket `asyncio.Lock` to `ConnectionManager`, created when a socket is registered
  (`connect()`) and also lazily on first use in `send_to()` (which is called *before*
  `connect()` for the `joined` event, per the v03.01 ordering fix — `send_to` must work for a
  not-yet-registered socket too).
- Acquire that lock around every `send_text()` call in both `broadcast()` and `send_to()`, and
  around `close()` in `close_room()`.
- Drop the lock entry in `_prune()` (and on a normal `disconnect()`) so it doesn't leak forever
  across many matches/reconnects.

**Dependencies:** None

**Expected result:**
Two concurrent `broadcast`/`send_to` calls targeting the same socket never interleave their
`send_text` calls -- one completes before the next starts.

**Acceptance criteria:**
- [ ] Every `send_text`/`close` call on a given socket is serialized by that socket's own lock.
- [ ] `send_to` works correctly for a socket not yet registered via `connect()` (the `joined`
      ordering case).
- [ ] Lock entries are cleaned up on prune/disconnect -- no unbounded growth.
- [ ] **Unit test:** two concurrent `broadcast()` calls (and, separately, two concurrent
      `send_to()` calls) targeting the same socket, using a fake socket that records whether any
      call started while another was still in-flight -- proves serialization, not just that both
      calls eventually complete.
- [ ] Ties to phase DoD; closes `v01.04-code-review.md` finding #1 (update its Status + Fixes
      applied in the same commit, matching the harden-findings convention, since this is the
      deferred finding's actual landing).

### ARENA-108 — End-to-end reconnect: a new connection reclaims a released seat

**Description:**
`assign_symbol` and `release_seat` already support a reconnect in principle (verified by reading
`server/match.py`: an already-released participant falls through to "assign the first free
symbol"), and this is unit-tested at that level (`test_release_seat_frees_symbol_for_reassignment`)
-- but nothing proves it end to end through the real WS endpoint: disconnect, then a *brand-new*
connection with the same token, receiving a real symbol back. Touches: `tests/` (and
`server/main.py` if this uncovers a real gap).

**What needs to be done:**
- Add a real-server integration test: join a match, connect, read `joined` (symbol assigned),
  disconnect cleanly, then open a **second, new** WebSocket connection with the **same token**,
  and assert its own `joined` event carries a real symbol (not `null`) -- proving the seat was
  genuinely reclaimed through the live endpoint, not just at the repository layer.
- If this test reveals any real gap in the reconnect path (it may not -- the primitives already
  look correct from reading the code), fix it as part of this same issue with its own explanation;
  otherwise this issue is confirmation-only, which is a legitimate and valuable outcome to record.

**Dependencies:** None

**Expected result:**
A participant who disconnects and reconnects (same token, new socket) gets seated again --
verified against the real server, not just the DB primitives in isolation.

**Acceptance criteria:**
- [ ] **Integration test (real server):** disconnect then reconnect with the same token yields a
      real symbol in the new connection's `joined` event.
- [ ] Any gap the test surfaces is fixed in this same issue, with the failure scenario recorded.
- [ ] Ties to phase DoD: "a player disconnecting mid-game frees their seat for a reconnect."

### ARENA-109 — Regression-guard the cancellation-safe cleanup primitive

**Description:**
architecture.md §10 names a specific hazard: a client-initiated drop can surface as async
cancellation rather than `WebSocketDisconnect`, which is exactly what broke in v01.04
(`asyncio.shield()` deadlocked; `anyio.CancelScope(shield=True)` is what actually protects the
seat-release write). Every existing disconnect test exercises the *graceful* path only -- nothing
regression-guards the cancellation path itself. Touches: `tests/`.

**What needs to be done:**
- Add a focused test on the exact primitive pattern `server/main.py`'s `finally` block relies on:
  a task blocked on a long-running operation gets cancelled (simulating the client-initiated drop),
  and a shielded cleanup operation inside its `finally` block still completes despite that
  cancellation. This directly targets the primitive-choice regression class (an accidental
  reversion to `asyncio.shield()`, or removing the shield entirely) rather than trying to force a
  real low-level TCP abort through the `websockets` client, which has no reliable public API for
  that and would make the test racy/version-fragile for no real gain in confidence.

**Dependencies:** None

**Expected result:**
A cancelled task's shielded cleanup still runs to completion; the test would fail if the shield
were ever removed or swapped back to `asyncio.shield()`.

**Acceptance criteria:**
- [ ] **Unit test:** a cancelled outer task's `anyio.CancelScope(shield=True)`-protected cleanup
      still completes (assert the cleanup's own side effect happened despite the cancellation).
- [ ] Test is fast and fully deterministic -- no real network/socket involved.
- [ ] Ties to phase DoD: "a client-initiated drop still runs cleanup (the cancellation path)."
