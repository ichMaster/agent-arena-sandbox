## Findings

### 1. 🟡 LOW — `MemoryWindow.entries()` leaks mutable internal state

**File:** `agent/memory.py` (`entries`)

**Failure scenario:** `entries()` does `list(self._entries)` — a new *list*, but the dicts inside it
are the same objects stored in the internal deque. `memory.entries()[0]["move"] = 999` would silently
corrupt the window's own recorded history, not just the caller's copy.

**Why deferred:** no code in this phase (or planned for v02.03, per its own read of `build_prompt`
as a read-only consumer) ever mutates a returned entry — `build_prompt` only reads `entry["type"]`/
`entry["player"]`/etc. This is the same shape of finding already accepted as deferred MVP scope for
`games/tictactoe.py`'s public `board` attribute in v01.01: real in principle, unreachable through any
actual call site today. Revisit if a future phase introduces a caller that holds and mutates entries.

## What's solid

- `AgentProfile.load_from_yaml` wraps both failure modes the DoD calls out (malformed YAML, a
  schema-invalid but syntactically-valid YAML) into a single clear `ValueError`, tested independently
  — neither a bare `yaml.YAMLError` nor a bare `pydantic.ValidationError` leaks past the function.
  A genuinely missing file is left as the standard, already-clear `FileNotFoundError` rather than
  needlessly re-wrapped.
- `MemoryWindow`'s eviction is tested against a **mixed** sequence of moves and chat (not just one
  kind), which is the case that would actually catch a bug in a hand-rolled ring buffer — though here
  it's `deque(maxlen=...)` doing the work, so the test is really pinning that the tagging/ordering
  logic around it doesn't break the guarantee.
- `build_prompt` has no I/O and makes no model call, matching §7.2 exactly ("the agent never
  round-trips to read state") and the phase DoD's own test note; every input is a parameter.
- `mypy games server agent` is strict-clean across all 18 source files.
