## Findings

### 1. 🔴 HIGH — `assign_symbol` doesn't handle a concurrent seat-assignment conflict

**File:** `server/repository.py:44-58` (`assign_symbol`)

**Failure scenario:** Two players join the same match and both request a seat at nearly the same
time (a realistic scenario — a match's REST `join` endpoint, coming in v01.03, will call
`assign_symbol` per request). Both requests read the `participants` table before either has
committed, both see `taken_symbols = set()`, both pick `"X"`, and both call `session.commit()`.
architecture.md §5.1 documents exactly this: *"`UNIQUE(match_id, symbol)` guards against a race
assigning the same symbol twice"* — but the guard is a database constraint, and nothing in
`assign_symbol` catches the `IntegrityError` it raises on the losing commit. That request's
`session.commit()` raises, unhandled, propagating out of `Repository` into whatever called it (a
v01.03 REST handler, a v01.04 WS handler) as a raw 500 / an uncaught exception on the socket —
never the graceful `None` (or a legitimately reassigned symbol) the seat rule is supposed to
produce. The constraint prevents *data corruption* (two players never actually end up sharing a
symbol) but does not, by itself, prevent a *crash*.

**Proposed fix:** catch `IntegrityError` around the commit; on conflict, roll back, clear the
tentative assignment, and re-read the now-current taken-symbol set once more (the losing request's
retry will correctly see the winner's committed symbol and either claim the other one or return
`None` if both are now taken).

### 2. 🟡 LOW — `reconstruct_game` doesn't surface a replay failure

**File:** `server/repository.py:79-86` (`reconstruct_game`)

**Failure scenario:** `apply_move`'s return value (`True`/`False`) is discarded during replay. If a
stored `moves` row were ever invalid (out-of-range, wrong turn, logged after game-over), the replay
would silently skip it rather than surfacing that the persisted log and the reconstructed game
disagree.

**Why deferred:** no code path today can produce such a row — `Repository.log_move` has no
legality check of its own (by design; validation is `games.apply_move`'s job, one layer up), but
nothing calls it yet outside tests, and v01.04's move-authority flow (§5.4) is explicitly
responsible for calling `apply_move` *before* `log_move`, making an illegal logged move
structurally unreachable once that flow exists. Revisit if v01.04 ships without that ordering
guarantee holding.

## Fixes applied

### Fix 1 — `assign_symbol` retries once against a fresh read after a conflicting commit

**Change:** `server/repository.py` — `assign_symbol`'s assignment loop now runs up to twice: on
`IntegrityError` from `session.commit()`, it rolls back, clears the tentative `participant.symbol`,
and re-reads the taken-symbol set before trying again. If both symbols are taken on the retry (the
concurrent winner took the last one), it returns `None` instead of raising.
**Regression test:** `tests/test_repository.py::test_assign_symbol_retries_after_a_concurrent_write_conflict`
— deterministically simulates the race by monkeypatching `session.commit` to raise `IntegrityError`
on the first call and succeed on the second, then asserts `assign_symbol` still returns a valid
symbol rather than propagating the exception.
**Verification:** `pytest tests/` → 52 passed (51 + 1 new); `mypy games server agent` → no issues
found in 8 source files.
**Architecture impact:** none — `assign_symbol`'s signature and return type (`str | None`) are
unchanged; this makes the method actually deliver the guarantee architecture.md §5.1 already
attributes to `UNIQUE(match_id, symbol)` ("guards against a race assigning the same symbol twice"),
rather than changing what that guarantee is.
