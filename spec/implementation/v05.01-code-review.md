## Findings

### #1 🟠 Binary frame not covered by the malformed-message fix (MEDIUM) — fixed
**Scenario:** `receive_text()` (Starlette's implementation, read directly, not assumed) does
`cast(str, message["text"])` on the raw ASGI message. If a client sends a **binary** WS frame instead
of text, the ASGI message carries a `"bytes"` key, not `"text"` — so `message["text"]` raises an
uncaught `KeyError`, propagating out of `_ws_connection` exactly like the pre-fix JSON-decode crash
did. Any of the app's three real actors (Web UI, agent CLI) only ever send text frames, but a raw or
malformed WS client could send a binary frame and crash its own connection the same ungraceful way
this issue's own fix just closed for bad JSON text — leaving the "malformed message... without killing
the socket" DoD only partially honored.
**Fix applied (`2ce9d81`):** wrapped `await websocket.receive_text()` itself in the same `try/except`
pattern, catching `KeyError` alongside the existing `json.JSONDecodeError`/non-dict handling, sending
`error_event("malformed message")` and continuing the loop. **Regression test:**
`tests/test_reconnect.py::test_binary_frame_keeps_connection` — `ws.send_bytes(b"\x00\x01\x02")`
yields the graceful error and the connection accepts a normal action afterward, mirroring the existing
malformed-JSON tests. **Verification:** 218 passed (217 → 218), `mypy --strict` clean (19 source
files).

## What's solid
The core `json.loads`/non-dict handling is correct and doesn't introduce a new wire shape — it reuses
the shipped `error_event`. `WebSocketDisconnect` still propagates correctly (Starlette raises it from
inside `receive()`/`receive_text()` *before* the key access that could `KeyError`, so the disconnect
path and the malformed-frame path stay cleanly distinct — verified by reading the exact call order in
Starlette's source). The new reconnect tests are deterministic (4/4 repeated runs) and exercise the
real seat/DB path, not a mock.

## Architecture impact
None — both fixes reuse the existing `error` event shape; no new event, no protocol change.
`spec/architecture.md` §6.2/§9-§10 already document this behavior class correctly; the code now
actually matches it.
