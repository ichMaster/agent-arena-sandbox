## Findings

### 1. 🟡 LOW — Reconnect test's seat-released check can race server cleanup

**File:** `tests/test_ws_reconnect.py`

**Failure scenario:** after `ws1`'s `async with websockets.connect(...)` block exits, the CLIENT
considers the connection closed (the closing handshake completed) -- but that doesn't guarantee
the SERVER's own handler coroutine has finished running its `finally` block yet (`receive_text()`
raising, then `manager.disconnect()`'s DB write). The test immediately opens a new DB session and
asserts `participant.symbol is None`. On a slower or more loaded machine, this assertion could run
before the server's cleanup task actually gets scheduled, making the test intermittently flaky --
not because the seat-release logic is wrong, but because the test doesn't wait for it.

**Why LOW, not MEDIUM/HIGH:** not observed failing across 10 stress-test runs in this environment;
this is a plausible latent flake, not a demonstrated one, and it affects only test reliability, not
production behavior (the actual `ConnectionManager.disconnect()` codepath this test exercises is
unchanged and already covered by `test_disconnect_releases_the_seat`).

**Proposed fix:** poll briefly (bounded, short interval) for `participant.symbol is None` instead
of asserting immediately, matching the retry-loop pattern already used elsewhere in this suite
(e.g., `tests/conftest.py`'s server-health poll) rather than inventing a new idiom.

## What's solid

- **The per-socket lock's lifecycle was traced through every real race, not just the happy path**:
  a lock popped by `disconnect()` while a *different* task still holds a reference to that exact
  `asyncio.Lock` object (via an in-flight `async with`) doesn't break that in-flight operation --
  Python's lock objects don't care whether they're still registered in the manager's dict, and the
  socket is already removed from `_connections` by the same `disconnect()` call, so no *new*
  broadcast could target it afterward either. Worst case on this path is a harmless failed send to
  an already-closed socket, already caught by `broadcast()`'s existing `except Exception:
  self._prune(...)`.
- **`_lock_for()`'s `setdefault` is safe under "concurrent" async calls** -- it's a fully
  synchronous dict operation with no `await` inside, so two coroutines racing to create the same
  socket's lock can't both win; Python's single-threaded event loop guarantees the whole call
  completes before any other coroutine gets scheduled in between.
- **Only one place in `server/main.py` calls a WebSocket method directly, bypassing
  `ConnectionManager`** (`websocket.close(code=4001)` for a bad token) -- checked it specifically
  because it would otherwise be an uncovered gap in the locking scheme; it's safe by construction,
  since it runs *before* `accept()`/`connect()`, when nothing else could possibly be targeting that
  socket.
- **The three cancellation-shield tests correctly isolate the primitive from the whole endpoint** --
  re-ran them mentally against anyio's actual cancellation semantics (not just trusting the test
  passed): the control test (no shield) genuinely needs the cancellation to interrupt the cleanup
  for the shielded test to mean anything, and it does.
