# Tracking system — implementation plan

**Status:** plan. No task below is started.
**Companions:** [ship-phase-tracking-vision.md](ship-phase-tracking-vision.md) (why · what the
dashboard shows) · [architecture.md](architecture.md) (contracts · formats · test strategy) ·
[dashboard/prototype.html](dashboard/prototype.html) (the target UI, already built).

**ID namespace: `TRK-###`.** Deliberately *not* `ARENA-###`, which belongs to the generated
application and whose counter continues across regeneration runs. The two systems have separate
lifecycles and must never share a numbering sequence.

---

## Decisions taken before task 1

These are settled here so no task has to re-litigate them.

| Decision | Rationale |
|---|---|
| **`tracker/` and `hooks/` are stdlib-only.** No third-party imports, no install step. | They run *inside* the pipeline. Anything requiring `pip install` can fail, and an emitter that fails is an emitter that can break a build (architecture §5.2). Zero dependencies is the only way to honour that guarantee. |
| **`dashboard/` gets its own `codegen/requirements.txt` and its own venv** at `codegen/.venv` (gitignored). | It needs FastAPI+uvicorn, and `pyproject.toml` is *generated by the run* — anything added there is overwritten. This closes the open question in vision §8. |
| **The dashboard runs on port 8420**, never 8000. | 8000 is the generated app's. Both may run at once. |
| **Python ≥ 3.11**, matching the generated project's floor. | `tomllib`, `datetime.UTC`, and exception groups are all available. |
| **`ruff` + `mypy --strict` over `codegen/`**, same bar as the app. | The tracker is real code and gets the repo's normal standard. |

## Step 1 — Tracker core

### TRK-001 — `codegen/` scaffolding + tooling

**Description:** Create the committed directory structure, the dashboard's dependency file, and the
lint/type configuration. No runtime behaviour.

**Implementation:**
- Create `codegen/tracker/`, `codegen/hooks/`, `codegen/tests/fixtures/`, each with `__init__.py`
  where it is a package.
- `codegen/requirements.txt`: `fastapi`, `uvicorn`, `websockets`, `pytest` — **dashboard and tests
  only.** Add a header comment stating that `tracker/` and `hooks/` must import none of these.
- `codegen/pyproject.toml` for tool config *only* (`[tool.ruff]`, `[tool.mypy] strict = true`,
  `[tool.pytest.ini_options] testpaths = ["codegen/tests"]`). **No `[project]` table** — this is not a
  distributable package and must not be picked up by the generated project's build.
- Verify no path under `codegen/` is caught by the inherited `.gitignore` (architecture §4.1 names the
  `lib/`, `build/`, `dist/` trap).

**Dependencies:** None

**Acceptance criteria:**
- [ ] `git check-ignore -v` returns nothing for every committed path under `codegen/`.
- [ ] `python3 -m pytest codegen/tests` runs and collects 0 tests without error.
- [ ] `mypy codegen/` and `ruff check codegen/` both pass on the empty tree.
- [ ] Installing `codegen/requirements.txt` is **not** required for `pytest codegen/tests` to run.

### TRK-002 — `schema.json` — the event contract

**Description:** Machine-readable JSON Schema for the event envelope and every event type, per
architecture §2–3. This is the single source of truth; the prose in architecture.md mirrors it.

**Implementation:**
- Draft 2020-12. Top-level: envelope fields (`v`, `ts`, `run_id`, `type`, `scope`, `status`, `data`,
  `emitter`) with `additionalProperties: false` on the envelope.
- `oneOf` per `type`, each pinning its **required `data` keys** from the architecture §3 table.
- Per-level `scope` requirements from architecture §2.3, expressed as conditional `required`.
- `ts` pattern-constrained to ISO-8601 UTC with milliseconds and a `Z` suffix.
- Ship a `validate(event) -> list[str]` helper in `tracker/schema.py` that returns error strings —
  **stdlib only**, so a hand-rolled validator over the schema rather than `jsonschema`.

**Dependencies:** TRK-001

**Acceptance criteria:**
- [ ] All 31 event types from architecture §3 are represented.
- [ ] A valid example per type validates; an example missing each required `data` key fails, naming
      the missing key.
- [ ] An `issue.*` event without `scope.version` fails validation.
- [ ] `validate()` imports nothing outside the stdlib.
- [ ] Architecture §2–3 and `schema.json` agree — a test asserts the type list in the doc table matches
      the schema's `oneOf` branches.

### TRK-003 — `emit.py` — append one event, never raise

**Description:** The only writer. Appends one validated, redacted event to the active run's log.

**Implementation:**
- `emit(type, *, scope=None, status=None, data=None, emitter)` per architecture §5.1, plus a
  `__main__` CLI for shell/hook callers.
- Resolve the run from `codegen/runs/current`; if absent, return silently (nothing to attribute to).
- Serialise with `json.dumps(..., separators=(",", ":"), ensure_ascii=False)`, append `\n`, encode.
- If the line exceeds **4096 bytes**, truncate string values in `data` to 512 chars and set
  `data._truncated = true`; re-serialise. Never split a line.
- `os.open(path, O_WRONLY|O_APPEND|O_CREAT, 0o644)` → **exactly one `os.write()`** → `os.close()`.
- Wrap the entire body in `try/except BaseException`; on failure best-effort append one line to
  `codegen/var/emit-errors.log` and return `None`.

**Dependencies:** TRK-002

**Acceptance criteria:**
- [ ] Never raises: parametrised over unwritable path, missing parent, non-serialisable `data`, absent
      `runs/current`, read-only filesystem — each returns `None`, writes nothing to stdout/stderr.
- [ ] Exactly one `os.write` call per event (assert via monkeypatch).
- [ ] A 100 KB `data` payload yields a line ≤ 4096 bytes carrying `_truncated: true`.
- [ ] **Concurrency:** 12 processes × 300 events → exactly 3600 parseable lines, 0 corrupt.
- [ ] An event failing `validate()` is not written, and the reason lands in `emit-errors.log`.
- [ ] Emitting 1000 events takes < 2 s wall-clock (it is on the pipeline's critical path).

---

### TRK-004 — Redaction

**Description:** Strip credential-shaped values before anything reaches disk. Architecture §8 — this
is the one security requirement, and it lives in the emitter so no call site can forget it.

**Implementation:**
- `tracker/redact.py`: `redact(obj) -> obj`, recursive over dicts/lists/strings.
- Patterns: `sk-[A-Za-z0-9_-]{16,}`, `ghp_[A-Za-z0-9]{20,}`, `github_pat_…`, `AKIA[0-9A-Z]{16}`,
  `xox[baprs]-…`, `(?i)(api[_-]?key|token|secret|password)\s*[=:]\s*\S+`,
  `(?i)authorization:\s*\S+`. Replace the value with `«redacted»`.
- Cap key depth and total scan size so redaction cannot itself become slow.
- Called by `emit()` unconditionally, after validation, before serialisation.

**Dependencies:** TRK-003

**Acceptance criteria:**
- [ ] A table of ≥ 10 secret-shaped strings, each embedded at a different nesting depth, never appears
      in output; `«redacted»` does.
- [ ] Redaction runs on **every** emit path including the CLI — no `emit()` overload bypasses it.
- [ ] A realistic 4 KB event redacts in < 1 ms.
- [ ] Non-secret text containing the word "token" in prose is **not** mangled (no false positives on
      `data.title` / `data.reason`).

### TRK-005 — Run context — id, `runs/current`, lifecycle

**Description:** Create and tear down a run: allocate the id, write the pointer, emit `run.start`
with the git context, refuse a second concurrent run.

**Implementation:**
- `tracker/run.py`: `start(command, plan, baseline) -> run_id`, `finish(status)`.
- Run id `run-YYYYMMDD-HHMMSS` from UTC. Create `codegen/runs/<id>/`, write `codegen/runs/current`.
- `run.start.data.git` from `git rev-parse --abbrev-ref HEAD`, `git rev-parse --short HEAD`,
  `git remote get-url origin`. Failures degrade to `null`, never abort.
- **Refuse to start** if `current` names a run with no terminal event — print the offending run id and
  exit non-zero (architecture §9.2: concurrent runs are unsupported, and must fail loudly, not corrupt).

**Dependencies:** TRK-003

**Acceptance criteria:**
- [ ] `start()` creates the directory, the pointer, and a schema-valid `run.start`.
- [ ] Starting while an unterminated run exists exits non-zero and writes no new run directory.
- [ ] Starting when the previous run has `run.end` succeeds.
- [ ] Git context is populated on this repo; in a non-git temp dir the fields are `null` and no
      exception escapes.

## Step 2 — Reducer

### TRK-006 — `reduce.py` — pure events → state

**Description:** Fold a log into the `state.json` shape (architecture §6). Pure: no clock, no
filesystem, no env.

**Implementation:**
- `reduce(lines: Iterable[str], now: datetime) -> State`. `now` is a **parameter**, never read
  internally — this is what makes golden tests possible.
- Assign `seq` as the 0-based line ordinal (architecture §2.2). Emitters never write it.
- Build the tree by `scope` path; pair `*.start` with `*.end`/`*.skipped`/`*.aborted`.
- Tolerance per architecture §5.3: torn final line → count and skip; malformed or unknown-type →
  `quarantine[]` with line number; **never discard silently**.
- Metrics: `issues_done`, `first_pass_rate`, `mean_issue_s`, `tests_passing`, `findings_open`, plus the
  `github` block from `issue.uploaded` / `issue.closed` / commit-bearing events.

**Dependencies:** TRK-002

**Acceptance criteria:**
- [ ] `reduce` contains no call to `datetime.now`, `time.time`, `os.environ`, or any file open —
      asserted by an AST test over the module.
- [ ] Reducing the same fixture twice yields byte-identical JSON.
- [ ] Open nodes get elapsed from the injected `now`; passing a different `now` changes only elapsed.
- [ ] `first_pass_rate` counts issues whose max `attempt` is 1, over issues with an `issue.end{ok}`.
- [ ] `github.commits` counts `issue.commit` + `finding.fixed` + `harden.finding.fixed` + release
      commits, not just issue commits.

### TRK-007 — Scope range + ETA model

**Description:** The two derived values that must never present a guess as a fact (vision §6.1).

**Implementation:**
- `scope`: `known` from versions with `version.decomposed`; `est_low`/`est_high` add
  `undecomposed × (3, 7)` issues, or `undecomposed × observed_mean` once ≥ 1 version is decomposed.
  **Emit no `issues_planned` scalar** — architecture §6 forbids it.
- `eta`: the three-term model from vision §6.1 (issues × mean, versions × review+release, phases ×
  harden). Weight by issue size once each of S/M/L has ≥ 1 sample; pooled mean until then.
- `eta` is `null` until at least one `version.end` exists. Always carries `basis`
  `{issues_sampled, undecomposed_versions}`.

**Dependencies:** TRK-006

**Acceptance criteria:**
- [ ] With zero completed versions, `eta is None` and `scope.known == 0`.
- [ ] With one completed version, `eta.low_s < eta.high_s` and `basis.issues_sampled` matches the
      count of `issue.end{ok}`.
- [ ] `scope.est_high - scope.est_low` **decreases monotonically** as `version.decomposed` events are
      appended, reaching 0 when none remain.
- [ ] No key named `issues_planned` appears anywhere in the output (asserted).

### TRK-008 — Golden fixtures + tolerance tests

**Description:** The committed fixture logs from architecture §10.2 and their expected states. This is
the core of the suite.

**Implementation:** Author each fixture in `codegen/tests/fixtures/` with a sibling
`<name>.expected.json`: `clean-run`, `retry-run`, `aborted-run`, `torn-tail`, `malformed`,
`skipped-versions`, `no-review`. A helper regenerates expectations behind an explicit
`--update-golden` flag, never by default.

**Dependencies:** TRK-006

**Acceptance criteria:**
- [ ] Each fixture reduces to its expected state exactly.
- [ ] `torn-tail` → `counts.torn == 1`, all preceding events still reduced.
- [ ] `malformed` → bad line and unknown type both quarantined with correct line numbers; the rest of
      the file still reduces.
- [ ] `no-review` → the un-reviewed version is **absent** from findings output, not present with zero.
      *(This pins the prototype's bug: "clean" and "nobody looked" are different claims.)*
- [ ] `aborted-run` → status `aborted`, unmatched `*.start` reported, no exception.

### TRK-009 — `state.json` writer + rebuild CLI

**Description:** Persist reducer output, and provide the offline rebuild path.

**Implementation:**
- Write atomically: temp file in the same directory, then `os.replace`. A reader must never observe a
  half-written snapshot.
- `python3 -m codegen.tracker.reduce <run-id>` rebuilds `state.json` from `events.jsonl`.
- Rewrite on each event when driven by the dashboard, but **debounce to ≤ 5 Hz** — the log can burst.

**Dependencies:** TRK-006

**Acceptance criteria:**
- [ ] Deleting `state.json` and rebuilding reproduces it byte-for-byte.
- [ ] A reader looping on `state.json` during 1000 rapid writes never reads invalid JSON.
- [ ] Rebuild of a 10 000-event log completes in < 2 s.

## Step 3 — `ship-phase` spine

### TRK-010 — Instrument `ship-phase`

**Description:** Emit the run/phase/version/step skeleton from the orchestrator. Smallest change that
produces a real timeline.

**Implementation:**
- One emit line per site in `.claude/skills/ship-phase/SKILL.md`: Step 0 → `run.start` (with the
  confirmed plan and baseline); per phase → `phase.start`/`phase.end`; per version →
  `version.start`/`version.end`/`version.skipped`; per sub-skill → `step.start`/`step.end`; blocked
  gate → `gate.blocked`; end → `run.end`.
- **One line per site, in the existing step's text.** Vision §8 names skill-file growth as an
  observer-effect cost — instrumentation must not restructure the skill.

**Dependencies:** TRK-005

**Acceptance criteria:**
- [ ] `ship-phase/SKILL.md` grows by ≤ 15 lines total.
- [ ] A dry `/ship-phase v01.01` on a scratch branch produces a log whose `*.start`/`*.end` pairs
      balance.
- [ ] The emitted plan matches the Step 0 confirmed plan, including dependency-filled versions.
- [ ] `--no-harden` produces `harden.skipped`, not a missing event.

### TRK-023 — Estimate/size step in both orchestrators

**Description:** Give the burn-down and the ETA a total before anything is decomposed. `ship-phase`
Step 0.5 *estimates* (issues do not exist yet); `ship-solution` Step 0.5 *counts* (its issues files do).

**Implementation:**
- `ship-phase`: per planned version, anchor the issue count on the roadmap **Tasks** list clamped to
  the 3–7 band `generate-issues` produces; infer a size mix (seam work skews M/L, additive work S/M);
  convert to points (S=1, M=3, L=5); project duration from prior runs' seconds-per-point, or state the
  assumed rate. Emit `run.estimate` with `source: "estimated"` and low/high per version.
- `ship-solution`: read counts and sizes straight from each issues file's summary table. Emit
  `run.estimate` with `source: "counted"`, `issues_low == issues_high`, and only duration projected.
- Reducer: at each `version.decomposed`, record signed error vs the estimate and a run-level bias.
- **Do not pass the estimate to `generate-issues`** — architecture §3.1.

**Dependencies:** TRK-010

**Acceptance criteria:**
- [ ] `run.estimate` is emitted exactly once per run, before any `version.decomposed`.
- [ ] `ship-phase` yields `source: "estimated"` with `issues_low < issues_high`; `ship-solution` yields
      `source: "counted"` with them equal.
- [ ] `generate-issues` receives no estimate: a grep of its invocation confirms no count is passed, and
      the produced issue count differs from the estimate on at least one version of a real run.
- [ ] Estimate accuracy appears per version in `state.json` as a signed error, plus a run-level bias.
- [ ] With no prior runs, the assumed seconds-per-point rate is stated in `rate_basis` rather than
      silently assumed.
- [ ] A `/ship-solution` burn-down shows **no scope band** — only the time axis is projected.

### TRK-011 — `version.decomposed` in `generate-issues`

**Description:** The event that makes scope discovery visible (architecture §3.2).

**Implementation:** Emit at `generate-issues` Step 2, after the issues file is written, carrying every

- [ ] `data.issues` length equals the rows in the file's summary table.
- [ ] Reducer moves that version from `undecomposed` to `known`, and `scope.est_high - est_low` shrinks.

## Step 4 — `execute-issues` and the remaining skills

### TRK-012 — Issue lifecycle events

**Description:** Per-issue events — the highest information density in the pipeline.

**Implementation:** Emit at the existing sites in `execute-issues`: 2a → `issue.start` (with `size`,
`area`), 2c → `issue.implement.end`, 2d → `issue.validate.end` (with parsed `pytest`/`mypy` counts and
`attempt`), 2e → `issue.commit`, end of loop → `issue.end`. Parse pytest's summary line and mypy's
final line for counts; on parse failure emit the event with `null` counts rather than skipping it.

**Dependencies:** TRK-010

**Acceptance criteria:**
- [ ] Every executed issue produces `issue.start` … `issue.end` in order.
- [ ] `pytest.passed`/`failed` and `mypy.errors` match the actual tool output for a sample issue.
- [ ] Unparseable tool output still emits the event, with `null` counts and `data.parse_error`.
- [ ] `attempt` increments within an issue and resets across issues.

### TRK-013 — Instrument the failure path

**Description:** **The task the whole system exists for.** `execute-issues` Step 3 reverts with
`git checkout -- .`, erasing the attempt; without an event here it is unrecoverable (vision §1).

**Implementation:** Emit `issue.failed` (with `attempt` and a classified `reason` —
`test-failure` / `type-error` / `import-error` / `timeout` / `other`) **before** the revert, and
`issue.reverted` immediately after. Capture the failing test names, redacted and truncated.

**Dependencies:** TRK-012

**Acceptance criteria:**
- [ ] A deliberately failing issue produces `issue.failed` then `issue.reverted`, in that order,
      **both before** the working tree is reverted.
- [ ] `reason` is classified, not raw output.
- [ ] Failing test names survive into `data`, truncated per the 4 KB budget.
- [ ] `git log` after the run shows no commit for that attempt — confirming the event is the *only*
      record, which is the point.

### TRK-014 — GitHub issue events

**Description:** Make created/closed/open countable.

**Implementation:** `upload-issues` Step 4 → `issue.uploaded` with `gh_number` and `url` per issue.
`execute-issues` 2g → `issue.closed`. Both are one line at an existing site.

**Dependencies:** TRK-012

**Acceptance criteria:**
- [ ] `github.created` equals `gh issue list --state all` count for the run's labels.
- [ ] `github.closed` equals the closed subset; `open == created - closed`.
- [ ] A workflow-B run with `gh` unauthenticated emits neither event and does not fail.

### TRK-015 — Instrument review, harden, release

**Description:** Findings lifecycle and release events.

**Implementation:** `review-and-fix-issues` Step 2 → `finding.raised` + `finding.classified` per

- [ ] A held finding emits `harden.finding.held` with a non-empty `reason`.
- [ ] `release.tagged.data.tag` matches the actual annotated tag created.

## Step 5 — Hooks and reconciliation

### TRK-016 — Hook scripts + registration

**Description:** The deterministic floor — events the model cannot forget to emit.

**Implementation:**
- `codegen/hooks/on_tool_use.py`, reading the harness payload from stdin.
- Register in `.claude/settings.json` with **only** a matcher and the command (architecture §7 — the
  single permitted file outside `codegen/`).
- Record tool name, argv[0], exit code, duration. **Never the raw command string** (§8).
- Attribute to the active run via `runs/current` and the most recent `issue.start`; best-effort.
- Exit 0 unconditionally; never write to stdout; complete in < 50 ms.

**Dependencies:** TRK-004

**Acceptance criteria:**
- [ ] Fixture stdin payloads (Bash, Write, Edit) each produce the expected event.
- [ ] Malformed/empty stdin → exit 0, no event, no stdout.
- [ ] A payload containing `ANTHROPIC_API_KEY=sk-ant-…` produces an event with no trace of the key.
- [ ] p95 runtime < 50 ms over 100 fixture invocations.
- [ ] `settings.json` diff is ≤ 10 lines and contains no logic.

### TRK-017 — `run.aborted` via Stop hook

**Description:** Close out a run killed mid-flight, so the dashboard need not guess from staleness.

**Implementation:** `codegen/hooks/on_stop.py` — if `runs/current` names a run with no terminal event,
emit `run.aborted` with `reason: "session-stopped"`.

**Dependencies:** TRK-016

**Acceptance criteria:**
- [ ] Killing a run mid-version yields `run.aborted`; the reducer reports status `aborted` with the
      unmatched node named.
- [ ] A cleanly finished run does **not** get a spurious `run.aborted`.

---

### TRK-018 — `reconcile.py` — compliance report

**Description:** Measure whether the skills actually emitted what they were told to. Architecture
§10.4 — this cannot be a unit test; it is a post-run analysis reporting a *rate*.

**Implementation:** Compare hook-observed `pytest` invocations against skill-emitted
`issue.validate.end`; compare `issue.commit` events against `git log`. Output a markdown report to
`codegen/var/` with a compliance percentage per skill.

**Dependencies:** TRK-016, TRK-012

**Acceptance criteria:**
- [ ] A synthetic log with a deliberately missing emit reports < 100 % and names the gap.
- [ ] A complete log reports 100 %.
- [ ] A commit present in git but absent from the log is flagged, and vice versa.
- [ ] The report **never fails the build** — it is a measurement, not a gate.

## Step 6 — Dashboard

### TRK-019 — Dashboard server — tail + WS

**Description:** Serve the UI and stream events.

**Implementation:**
- FastAPI on **port 8420**. `GET /` → the static page; `GET /api/state` → current `state.json`;
  `WS /ws` → snapshot on connect, then per-event deltas.
- Tail `events.jsonl` by polling size + incremental read (no watchdog dependency).
- Reads only `codegen/runs/`; writes only `codegen/var/` (vision §3 principle 6).
- Imports nothing from `server/`, `games/`, `agent/`.

**Dependencies:** TRK-009

**Acceptance criteria:**
- [ ] Starts and serves with the application tree **entirely absent** — its normal state between runs.

## Definition of done for the whole plan

- [ ] A real `/ship-phase` run produces a complete, balanced log with no manual intervention.
- [ ] The dashboard shows that run live, from first event to release tag.
- [ ] `pytest codegen/tests` green; `mypy codegen/` and `ruff check codegen/` clean.
- [ ] The reconciliation report shows ≥ 95 % skill compliance.
- [ ] `rm -rf codegen/` leaves a working repo — nothing outside it depends on the tracker.
- [ ] No secret appears anywhere in any log, verified by grepping a real run's events for the key
      patterns.

## Out of scope

Token and cost accounting (not observable from inside a run — vision §8) · multi-run concurrency
(architecture §9.2) · alerting or notifications · persisting runs to any remote · authentication on
the dashboard, which binds to localhost only.
